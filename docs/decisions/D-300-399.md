# Decisions D-300 to D-399

One heading per decision: what was decided, why, and its status. The exact rules are in the code, its tests and `docs/agent/`. How this log is organized: [DECISIONS.md](../DECISIONS.md).

### D-300 — One-tap record operations

A button or list row can change records with one tap: create an entry, set a value on all matching entries, open a new-record form, or on each row set, toggle, increment, create or open. Records cannot be deleted this way. A row shows the first of its actions whose condition is met.

**Why:** Check-ins, water counts, clock in and out, and mark-as-paid all fill in one value the user would otherwise type, and a few operations cover them.

**Status:** Decided

### D-301 — Values an operation can write

A one-tap action can write only a choice option, a number, a tick, today, now, or clear. It cannot write text, notes, attachments, schedules, or computed values. A bad value gets a message saying what it should be. The founder has yet to confirm this scope; for now only these values are allowed.

**Why:** Text is the user's content, which the AI must not write; the other values are fixed structure or unrelated to content.

**Status:** Awaiting the founder

### D-302 — Buttons have only create, setAll and open

A button can create a record, set a value on a filtered set of entries, or open a form, but it cannot change one specific record. Set, toggle and increment work only on list rows. A create button must not leave a required field empty, so the check asks for a prefilled form instead.

**Why:** A button does not know which record to change, and one record per tap is simple to undo while stats still add up.

**Status:** Decided

**Changed later by:** D-338.

### D-303 — Execution and undo

A one-tap change runs only when tapped. A newly created entry is removed on Undo, and an edited one goes back to its old value. Rapid taps stack, and Undo steps back once. If the record is gone, nothing changes. A bulk change asks first and is refused above 200 entries. Superseded by D-385: only deletion now shows Undo.

**Why:** A one-tap action must be quick, so it is not confirmed first, but a mistake must reverse at once; a bulk change may touch many records, so it asks first.

**Status:** Decided

**Changed later by:** D-385.

### D-304 — The AI's boundary and the checks

The AI can configure these buttons and row actions but cannot see records. Checks reject a missing table or field, or an action that does not fit a field's type, and say what fits. Deleting a table or field also removes the buttons that used it, and the change says how many were removed. The change goes into a draft first.

**Why:** A wrong button only stops working, and a deleted field should not be blocked by one button that used it.

**Status:** Decided

### D-305 — Month-calendar look for the record list

A record list can show a month calendar. Each day is shaded by how many entries it holds, or colored by the option of its latest entry with a legend. Users swipe between months and tap a day to list its entries, and the day and week starts follow the settings. The color choice still awaits the founder's confirmation.

**Why:** On the record list the calendar keeps its filter, sort and tap-to-edit; a review found streak calendars too small, so the cells fill the screen width.

**Status:** Decided

### D-306 — Display format of the right-hand field

A list row can show a running or finished time from a start field to an end field or to now, and a progress ring or bar toward a goal. Running times update every second. Only the list shows these; the stored value, exports and the record page keep the plain value. Not showing them on the record page awaits the founder's confirmation.

**Why:** The same field elsewhere still needs its plain value, and a running timer makes no sense in an export; the goal may be another field, known only where it is shown.

**Status:** Decided

### D-307 — Goal for a stat

A stat can have a positive number as its goal, shown as value over goal with a progress ring and percentage. When grouped, each row gets its own bar. A missing value counts as zero. Days-since and average-interval stats cannot have a goal.

**Why:** Water, weekly workouts and budgets need a target; a stat has no other record to take a goal from, so only a fixed number is allowed.

**Status:** Decided

### D-308 — Compare a stat with the previous span

A stat can compare with the same part of the previous span, such as this week up to today's weekday against last week, and shows the change as a percentage or as an increase or decrease. Arrows are neutral, not red and green. The filter must hold exactly one period condition. Streak and average-interval stats cannot be compared. The same-period choice awaits the founder's confirmation.

**Why:** Comparing half a month with the whole previous month always looks like a drop; same-period comparison is the usual bookkeeping practice.

**Status:** Decided

### D-309 — Version and prompt for phase C2

The schema version goes up one step, and the AI prompt gets rules for the month calendar, the timer and progress display, and stat goals and comparisons. The new options are optional, so existing configs need no change beyond the version number.

**Why:** Two parallel branches changed the same list and migration, so the version number is set again when merged.

**Status:** Decided

### D-310 — Add entry point for lists

When a change adds a record list to a table that has no way to add entries, the change also adds an Add button above the list that opens the full form with the first ten fields. Only one is added per table, and lists that already existed are left alone, so a button the user removes stays removed. The founder chose on 2026-10-30 to fix this first.

**Why:** On a phone test a new habit list had no way to add entries; the prompt asks for a form but the model often misses it, so the core now guards it.

**Status:** Decided

**Changed later by:** D-349.

### D-311 — Big-circle look for the record list

A record list can show each record as a large circle with its title below, three per row. A tap runs the circle's first matching action or opens the record; with a goal the circle shows a progress ring. When actions exist, a long press opens the record rather than editing the component. The founder confirmed this on 2026-10-30. Its Undo was superseded by D-385. Changes D-235.

**Why:** A screen of circles that a tap checks in, like popular streak apps; it reuses the list's filter, sort and actions and adds no new component type.

**Status:** Decided

**Changed later by:** D-385.

### D-312 — Big circles show at most 24

(`MAX_TILES` in `core/board-view.ts`): `limit` is still 1–100, `tiles` draws only the first `min(limit, 24)`, and check reports no error

**Why:** Streaks deliberately limits to 24, and some reviewers liked the cap: everything on one screen with no scrolling. Truncation rather than an error, so a model writing `limit: 30` does not get the whole change rejected

**Status:** Decided (confirmed by the founder on 2026-10-30 in the popular-app-feature-cloning session, with the default of 24)

### D-313 — Kanban look for the record list

A record list can show its entries as columns, one per option of a single-choice or reference field in option order, with an Unsorted column for entries that have no value. Cards show the title and chosen subtitle fields, and the columns scroll sideways.

**Why:** Task boards, sales stages and order status all need columns, without a separate status field type.

**Status:** Decided

**Changed later by:** D-351.

### D-314 — Moving a card on the board

On a board a card can move to another column by long-press and drag, or by tapping it and choosing Move to, which screen readers can also use. Tapping a card now shows a menu of Open, Move and Cancel rather than opening it directly. Its Undo was superseded by D-385. The founder accepted this default on 2026-10-30. Changes D-235.

**Why:** Dragging is unusable for screen readers and for people with limited hand function, so a tap-based way is needed.

**Status:** Decided

**Changed later by:** D-385.

### D-315 — Version and prompt for phase C3

The schema version goes up one step, and the AI prompt gets rules for big circles and boards. These new looks go into a draft first, and the AI still cannot see record content.

**Why:** Like the earlier phases, one version bump per phase, with its rules appended at the end.

**Status:** Decided

### D-316 — Reminders by record (plan P8)

A reminder can now fire for each record that has a schedule, at its own time, according to that record's rule. It sits in the same reminder list with its own limit of ten, and is removed with its table or field. Each record gets its next seven occurrences. The notification title is the record's name; the AI writes only the generic body text. Tapping it only opens the page set for the reminder.

**Why:** Habit, plant and medication apps need each item to have its own time, and the AI learns just one more kind of reminder.

**Status:** Decided

**Changed later by:** D-346.

### D-317 — Reminder condition `unless`

A per-record reminder can be skipped when a matching record already exists in the same day, week or month, such as today's check-in already being done. Later occurrences are judged by current records too. The judgement happens on the phone, and the AI writes only the condition.

**Why:** It stays quiet when the task is already done in that span, and each occurrence is judged so that later days can be decided in advance.

**Status:** Decided

### D-318 — "Done" and "Remind me later" buttons on the notification

A per-record notification can carry a Done button, which writes one change to that record, and an optional Remind me later button, which schedules a new reminder a few minutes on (5 to 240 minutes). The buttons do not open the app, and they write directly to the database without the AI and without creating a version. The founder confirmed on 2026-10-29 that this is allowed.

**Why:** Medication and habit check-ins are most often marked done straight from the notification.

**Status:** Decided; not verified on a device

### D-319 — Limit on pending system notifications

iOS allows only 64 pending notifications, so the app keeps the nearest ones itself: regular reminders first, then due and per-record reminders by nearest time, with per-record ones capped at 40. Changes are diffed by ID so only the difference is cancelled and scheduled. The cap of 40 awaits the founder's confirmation.

**Why:** Past 64, iOS drops extra notifications without regard to time, so trimming them ourselves keeps the nearest ones.

**Status:** Decided

### D-321 — Home-screen widgets

Home-screen widgets can show a stat, a button, or a record list in list, card or checklist look, drawn from the same config and rules as the page. The phone computes the data and writes it to a local file, and the widget only draws it; the AI never sees it. Month calendar and kanban are not supported, and iOS widgets need iOS 17 or later.

**Why:** A widget cannot run the app's code, so it only reads computed results, and sharing the config and rules keeps widget and page consistent.

**Status:** Decided

### D-322 — When widgets refresh

A widget refreshes when the live config, records, placed widgets or language change, and writes only if its content changed. Each snapshot holds today and tomorrow, so the widget switches to tomorrow at midnight without the app opening. If the app has not been opened after that, the widget says to open Morph for updates.

**Why:** A widget cannot compute on its own; computing one day ahead covers the common morning glance, and anything further is guessing.

**Status:** Decided

### D-323 — Tapping on a widget

A widget can only create an entry, or run a tile's row action, without opening the app. The tap is queued, and the app executes it when it next runs, dated to the moment of tapping, with a banner reporting the count. Buttons that change many records, open a form or open a page still open the app. Undo for the batch was superseded by D-385.

**Why:** The widget cannot write the app's database, so the app does all writes with one writer, and the day of the tap is kept even when the app opens late.

**Status:** Decided

**Changed later by:** D-385.

### D-324 — Android widgets use RemoteViews, not Glance

Android widgets use RemoteViews, the system's built-in widget toolkit, rather than Glance. This needs no new dependency or build setup, and it is enough for text, short lists and small circle or ring images.

**Why:** One dependency and one build configuration fewer, with no loss of function.

**Status:** Decided

### D-325 — "Put on the home screen" is the user's own action and does not go into the config

Putting a component on the home screen is a user action from the long-press menu, and the placement is kept on the device rather than in the config. The AI cannot add such an entry to a page. Android asks the system to confirm placement; on iOS the user adds the widget from the widget gallery and picks the component in Edit Widget.

**Why:** Placing something on the home screen touches the user's own space, so the user must tap it; an AI-made entry would start it for them.

**Status:** Decided

**Changed later by:** D-342.

### D-326 — Scan pack edge detection no longer takes a large table on the paper for the paper

Scan edge detection now chooses among several candidate outlines and rejects any that is a frame drawn on the paper itself, so a table inside a bill is no longer taken as the page. If every candidate is such a frame, the whole photo is used. A white background or a shadow at a corner can still lead to a wrong crop. (The founder, 2026-10-29.)

**Why:** On a real Android phone a table inside a bill was taken as the page, so the user had to tap whole photo by hand.

**Status:** Decided; not verified on a device

### D-327 — iOS edge detection uses the same `pickPaper`

On iOS the same paper-choosing logic is used, instead of the system's detection alone, so both platforms pick alike. A white cloth may still be taken as the whole photo. Checked by unit tests and a simulator probe, not on an iPhone.

**Why:** The iOS system detector also picked the table frame when paper filled the photo, so both platforms need one selection method.

**Status:** Decided; not verified on a device

### D-328 — Scan to Word

Adds Scan to Word: each image is recognised, its layout analysed, tables rebuilt, and the text written as a Word file with one page per image, all on the phone. The result page lets the user select, edit, delete and undo each block, and tables open the Excel editor. Electronic PDFs are not converted. The founder decided this in conversation on 2026-10-28/29.

**Why:** In-app editing was wanted and nearly usable output is enough; the work is done on the device, and recognised text never leaves it.

**Status:** Decided; not verified on a device

**Changed later by:** D-335, D-362, D-366, D-463.

### D-329 — Layout analysis model PP-DocLayout-S

a separate pack `layout` 1.0.0 (2.65 MB), separate from `ppocr` and `dewarp`: the Paddle model of Hugging Face `PaddlePaddle/PP-DocLayout-S` (Apache-2.0) converted to ONNX with paddle2onnx 2.1.0, `scale_factor` fixed at [1, 1], only the first output kept, weights stored as fp16 (still float32 when computing), so flattening's `modelRun` can run it without changing native code. For convert-to-Word it is asked together with the text recognition model (D-299), optional: converting still works without downloading, it just doesn't separate titles and images. Score threshold 0.3 (0.45 for images); table regions are not used (tables are recognized only with ruled lines), an "image" with many characters or more than half a page is treated as body text, and duplicate images are removed

**Why:** word-exp compared S and M on 19 sample pages: S 4.9 MB (fp16 2.6 MB), about 50 ms on the Mac; M 23.5 MB (fp16 12 MB), about 220 ms. M is slightly better on title and body blocks, and both recognize a whole dense form page as one image, needing the same post-processing. The fp16 weights give the same results as fp32

**Status:** Awaiting the founder: model hosting (the files are not yet uploaded to R2)

### D-330 — Fonts and paragraphs for convert-to-Word

Convert-to-Word now uses a sans-serif default font (Arial for Western text, Microsoft YaHei for Chinese) and bold headings. A paragraph whose first line is clearly indented gets a first-line indent, and a title cannot be a quoted line of dialogue or a long sentence. Improves on D-328.

**Why:** The founder compared CamScanner on 2026-10-30: ours used a serif font, lacked first-line indents, and took dialogue for a title.

**Status:** Decided; not verified on a device

**Changed later by:** D-463.

### D-331 — Side-by-side rows in convert-to-Word

In convert-to-Word, blocks that sit side by side, such as the three tables of a payslip, are written as one borderless layout row with a cell per column, instead of one column. The edit page shows them left and right, and a row is deleted when all its cells are emptied. Improves on D-328.

**Why:** The founder compared CamScanner on 2026-10-30: a payslip's side-by-side tables were laid out in a single column.

**Status:** Decided; not verified on a device

**Changed later by:** D-366.

### D-332 — Form labels and values in convert-to-Word

In convert-to-Word, a label and its value on the same line become a two-column borderless table, one pair per row, when the labels end with colons or there are two or more pairs. Previously each was its own paragraph. Improves on D-328.

**Why:** The founder compared CamScanner on 2026-10-30: on a payslip, labels and their dates were split into two paragraphs.

**Status:** Decided; not verified on a device

### D-333 — Several lines in one cell are not split into several rows

Several lines inside one table cell stay in that cell instead of being split into rows, unless at least half of the rows fill two or more columns. In convert-to-Word, cell text goes one line per row of the original. The same rule applies to convert-to-Excel.

**Why:** The founder compared CamScanner in conversation on 2026-10-30: lines in an energy-diagnosis header box were split into several rows.

**Status:** Decided; not verified on a device

**Changed later by:** D-536.

### D-334 — Convert-to-Word drops margin debris

Convert-to-Word drops stray marks at the page edge: short, low-confidence text away from other text is not written. Short text recognized reliably, such as numbering, is kept, and page numbers are still removed. Improves on D-328.

**Why:** The founder compared CamScanner in conversation on 2026-10-30: a '00' from a margin smudge appeared at the top of a page.

**Status:** Decided; not verified on a device

**Changed later by:** D-536.

### D-335 — Font sizes in Word conversion follow the proportions of the original

Convert-to-Word follows the font proportions of the original: form text can be as small as 6 pt, text pages stay at 9 to 12 pt, and table text shrinks with its table, down to 5 pt if the longest word would not fit. Each run is written at its own page's size. Changes the body-text limit of D-328.

**Why:** The founder compared CamScanner in conversation on 2026-10-30: the original form text is about 6 pt, and our tables ran over two pages.

**Status:** Decided; not verified on a device

**Changed later by:** D-536.

### D-336 — Stats and charts group by reference fields

Stats and chart groupings can use a reference field, not only a single-choice field: each record of the referenced table is one group, titled as in that table, and records pointing to nothing or to a deleted record count as 'Not set'. The founder agreed to add it on 2026-10-30.

**Why:** Categories, customers and projects often have their own table, and previously one could not total spending or hours by them.

**Status:** Decided

### D-337 — Stat subtraction

A stat can show one total minus another with `stat.minus`, and the subtracted total may come from a different table. Only count and sum are allowed, it cannot combine with grouping or comparison, and removing the subtracted table removes the stat too. Only one subtraction was possible.

**Why:** Money left to assign in a zero-based budget belongs to no single table, and one stat can read only one table.

**Status:** Decided

**Changed later by:** D-new-summary-blocks-1.

### D-338 — Create and open the form

A button's or list row's create can open the new-record form with values preset, instead of saving at once, so the user completes and saves it. It cannot run from a reminder's Done, which needs the app open, and on a home-screen widget it only opens the app. Changes D-302.

**Why:** Previously a list row could not create a record whose amount the user must fill in, such as a category assignment or a fuel-up.

**Status:** Decided

### D-340 — Schedule "once"

A repeat rule can be 'once', with an optional date: it is done a single time, then has no next occurrence, and an undated one means do when there is time. Lists show only the date or status, and the editor offers Today, Tomorrow, Next week and No date. The founder agreed to add it on 2026-10-30.

**Why:** One-off and repeating tasks are the same kind of thing, and one-offs used to need a separate date field and still remind after being done.

**Status:** Decided

### D-341 — Doing it early counts as this occurrence

For a to-do on fixed days (every day, certain weekdays, certain days of the month or year), doing it early counts as this occurrence: the next one is the first scheduled day after the one that was due. The field's `countEarly` setting turns this on. When it is off, early completion does not count, as with bills. The AI sets it by purpose.

**Why:** Ticking off a to-do early looked like it had not gone away, while bills still need the old rule.

**Status:** Decided

### D-342 — Pages made for a single record

A page can be made for one record: tapping an entry in a list opens this page, titled with that record, instead of the edit form. Its components can use `$record` to mean that record, for example in filters and presets. Such a page cannot go in the navigation bar, a button or the home screen. Deleting its table now also removes the page (see D-373). (The founder, 2026-10-30.) Changes D-250, D-325.

**Why:** Pages like project-to-tasks need a per-record view, and the AI cannot name a specific record, so `$record` stands in.

**Status:** Decided

**Changed later by:** D-373.

### D-343 — Preset values for the quick-add form

A quick-add form can preset values the user does not see, such as the project a task belongs to, and saves them with the record. On a record page the value can be `$record`. A field cannot be both shown in the form and preset, and at most 10 values can be preset.

**Why:** The quick add on a project page should already know which project, so the user does not choose it again.

**Status:** Decided

### D-344 — Recognizing dates in text on the device

Chinese, English and French dates, times and repeat rules (such as 'next Friday' or 'every Monday') are recognized on the phone by fixed rules, not by the AI. The quick-add form and date boxes use them to fill a date, and a wrong match can be dismissed. The founder decided on 2026-10-30 to include it.

**Why:** Typing a date in one line is what people praise most in Todoist, and recognizing it on the phone keeps the text there.

**Status:** Decided

### D-346 — Schedules with a time of day

Every kind of schedule rule can carry a time of day, such as 'Tomorrow 03:00' or 'Every Monday 09:00'. Items on the same day sort by time, and a reminder uses the record's own time, or the rule's time if it has none. The AI may set the time only in the field's default. The founder set the order of this batch on 2026-10-30. Changes D-316.

**Why:** Todoist tasks and things like medication or classes have a time, and a time in the rule avoids a separate time field.

**Status:** Decided

### D-347 — Record list sections

A record list can be split into sections: by single choice or reference (one per option or record, with empty ones optionally shown), by date (day, week or month), and by schedule (Overdue first, No date last). Sections have titles and counts, can be collapsed, and `limit` caps the items per section. Not done: dragging items between sections.

**Why:** Todoist's inbox and today views split by day, and bookkeeping by day or journals by month need the same split.

**Status:** Decided

### D-348 — The month calendar understands schedule fields

A month calendar can show a schedule field: each upcoming occurrence falls on its day, overdue items fall on today, and finished one-offs and items without rules are hidden. Past months show no repeating items. The week strip look is not done yet. Changes D-295, which did not allow schedules here.

**Why:** After to-dos moved into schedules, the calendar would miss them, and so would watering, bills and maintenance.

**Status:** Decided

### D-349 — Add in place

A record list can add in place: a plus beside each section title (none for Overdue), an 'Add on' button under a selected calendar day, and an 'Add' at the bottom of an unsectioned list. The new-record form opens with that section's value preset, and the user still completes and saves it. D-310's extra 'Add' button is no longer added beside such a list.

**Why:** A task added in a section should belong to that section, and one added on a chosen day should be for that day.

**Status:** Decided

### D-351 — Board columns by reference field

A board's columns can come from a reference field: one column per record of the referenced table, plus 'Not set', and dragging a card to a column sets its reference. A new `groupFilter` (up to five conditions) chooses which columns appear, so a project page shows only its own. Its undo is superseded by D-385.

**Why:** Each project has its own sections, and a single choice's options are global, so the user cannot add them.

**Status:** Decided

**Changed later by:** D-385.

### D-352 — Quick add that pops up from the bottom

A quick add can open as a sheet: a round '+' at the bottom right of the page brings up an add box from the bottom with the keyboard ready. The box stays open and clears after each add, tapping outside closes it, and Done on a single-line box adds the item. Not done: laying out non-text fields as a row of small buttons.

**Why:** In Todoist a '+' at the bottom right works in any view, while an inline form takes space at the top and means scrolling back.

**Status:** Decided

### D-354 — Mistakes made when really building the Todoist sample with the AI

Validation now rejects a row button that writes a schedule's last-done field while requiring that field to be empty. The AI prompt also says how to build a to-do table: 'next' gets a Done button, lists filter out finished items, subtasks add two rollups and are kept out of 'next', and a per-record reminder's Done creates a completion record and snoozes 30 minutes.

**Why:** Building a Todoist sample from one sentence showed that a weekly item vanished after one Done tap and finished tasks stayed on the board.

**Status:** Decided

### D-355 — AI suggests the next step

After each change that applies, the AI suggests up to two things the app would often add next, in the interface language, without doing them. New suggestions replace old ones, undo clears them, and tapping one fills the input box. The founder said on 2026-10-30 that the AI could make suggestions.

**Why:** Otherwise the user has to know for themselves what to ask for next.

**Status:** Decided

### D-357 — The file room's working files and version stack

When files are put on the desk, each gets a working copy, and originals are never touched. The desk keeps a version for each tool use or continuous run of edits, which can be undone or redone, up to 20 versions or 500 MB, whichever comes first. After 7 days untouched, Settings suggests clearing it, and nothing is deleted automatically.

**Why:** Originals must stay untouched, and the founder confirmed the limits, the 7-day suggestion and merging of edits on 2026-10-30.

**Status:** Decided; not verified on a device

### D-358 — The room's layout is config

The file room's layout is set in config: toolbar at the bottom or top, a preview that fills the space or is large or medium, an optional file strip, up to two components above and below the preview, and a toolbar per file kind. The structure cannot hide the preview, touch files or act for the user, and items pointing to missing actions are not shown.

**Why:** The founder decided on 2026-10-30 that the layout can be changed, but the preview cannot be removed or touch files.

**Status:** Decided

### D-359 — The room's default toolbar is generated from the action registry

The room's default toolbar is generated from the action registry: a tool appears for each file kind its input names, and office files get only tools that take documents and no images or PDFs. Tools fall into Edit, Adjust, Convert and Quick actions (at most 8), and run as a two-step workflow on the desk's files.

**Why:** The toolbar follows the actions that exist instead of a second hard-coded list, and the existing executor runs it.

**Status:** Decided; not verified on a device

**Changed later by:** D-363.

### D-360 — The room page (R1)

The room page is full screen with a large preview: images zoom, PDFs turn pages (using the optional PDF pack), and videos play. Conversion results are read-only, and each tool run adds one version. Done offers save, share, print and system preview; D-462 later removed keep and clear from it. Editing in the room came later (D-366).

**Why:** The founder confirmed on 2026-10-30 that the large preview and the editor are one view, so the first version is read-only.

**Status:** Decided

**Changed later by:** D-363, D-366, D-462, D-509.

### D-361 — The inbox puts "Put on the desk" first

After files are received, the inbox's first item is 'Put on the desk', which copies them into the file room. Quick-action suggestions, 'See all' and 'Tell Tinkrum what I need' stay below. Nothing runs automatically, and the desk's copies are the batch's own. Not shown for files that are too large. Changes the inbox layout of D-117, D-208 and D-237.

**Why:** The founder answered on 2026-10-30 that the flow should add no extra step and lose no recommendations.

**Status:** Decided; not verified on a device

**Changed later by:** D-457.

### D-362 — How the later stages of the file room are settled

The founder's answers of 2026-10-30 fix the later file-room stages: the large preview is the editor, a saved Excel or Word file can be put back on the desk for editing, and Word and Excel editing comes next. Not done: a button offered after three identical runs, PDF text editing, AI erase, live long-video viewing and multi-device sync. Changes D-066, D-082, D-111, D-127, D-203, D-272, D-298, D-328.

**Why:** Users expect a file made in the app to stay editable later, and the founder chose these answers in conversation.

**Status:** Decided

**Changed later by:** D-509.

### D-363 — When a single tool in the room runs directly; the toolbar always has a "Files" group

Parameter panels ask only for parameters not marked `ask: false`, and a tool with nothing to ask runs directly. Text recognition, the language for convert-to-Excel and convert-to-Word, the recognition range and the document-to-PDF paper size do not ask. ### D-368 — Config v34: data · containers · tools

(`schemaVersion` 34). Data = three layers of value, record and table (`data.tables`, `data.calendar`; user files are a system table `$files` with a read-only structure); containers = everything the user sees (`containers.pages[].blocks`, `containers.desk`, `nav`), every block has the same 6 keys (`look`, `show`, `source`, `tools`, `opens`, `children`), and there are 23 looks; tools = things that write and produce (standalone `tools[]`: quick actions, reminders; in place: the one-tap record tools inside a block); `packages` are the added tool packages. **Containment and reference are separate**: a container holds only containers (a group can hold at most one more level of group), and refers to data and tools only by reference (`source` reads, `tools` references, `opens` navigates). **Two layers**: the user's app is entirely in the config and the AI can change it (into a draft, undoable); the Morph system layer (AI page, drafts, Change history, Settings, the inbox shell, the guide, the record edit page) is not in the config and can only be referenced as a target. v33 → v34 is one migration, and the same data reads out the same as in v33 (`v34-equivalence.test.ts`, also run on Hermes); the words shown to the user in the UI do not change (D-112)

**Why:** 39 operations and 21 components, each with its own way of reading data, are hard for both the AI and people to remember; once split into "reads, writes, holds", every relation can be enforced by the config check and written into the prompt

**Status:** Decided (branch `claude/v34-config`)
