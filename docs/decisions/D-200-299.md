# Decisions D-200 to D-299

One heading per decision: what was decided, why, and its status. The exact rules are in the code, its tests and `docs/agent/`. How this log is organized: [DECISIONS.md](../DECISIONS.md).

### D-200 — Measure taps and time for three tasks against other apps

For three tasks, record the number of taps and the time for first and repeated use, and compare with single-purpose apps on the same device. A measurement method and real route counting are in place: video compression 3/3, PDF compression 3/3, combining two ID photos into a PDF 6/6 in-app taps; this excludes the system picker, the system share sheet and manual crop adjustment.

**Why:** Verify the goal of saving steps only with actual measurement, and do not treat automated run time as human usage time.

**Status:** In progress: only automatic counts exist (the second run did not take fewer taps than the first); simulator, timing and comparison apps not yet measured

### D-214 — Rotate video

`video.rotate {degrees: 90/180/270}` rotates clockwise relative to the current picture, with 270 meaning to the left. iOS changes preferredTransform and then exports the encoded samples unchanged, using MOV when the MP4 container is not compatible; Android Media3 rotates and re-encodes. Original sound and duration are kept. Preset "Turn a video upright", video tool 1.6.0

**Why:** The founder decided on 2026-10-24 to fill in the video features

**Status:** Decided

### D-215 — Crop video to a ratio

`video.crop {ratio}` supports 9:16, 1:1, 4:5, 16:9; the first version crops at the center and offers no position adjustment. It straightens first and then trims the edges, rounds to the encoder's even pixels, and does not stretch; sound and duration are kept. Both ends re-encode to MP4. Preset "Crop to a vertical video", video tool 1.7.0

**Why:** The founder decided on 2026-10-24 to fill in the video features; centering is the handoff default

**Status:** Decided

### D-216 — Video speed

It is not frame-interpolated slow motion. Preset "Speed up or slow down a video", video tool 1.8.0

### D-241 — Your own key supports any provider

"Settings → AI → My own API key" first picks a provider: ① **Anthropic**: as before (`createHttpCompleter`; thinking effort, prompt caching and the server-refusal fallback are sent only here); ② **OpenAI-compatible API**: the user fills in the Base URL, model name and key (can be left blank, for local models), and the App calls `POST {Base URL}/chat/completions` (`packages/planner/src/openai.ts`: the system prompt goes into a system message, only `model` and `messages` are sent, and not `response_format`, `max_tokens` or `temperature`, because not every vendor supports them). OpenAI, OpenRouter, DeepSeek, Gemini and Groq have buttons that help fill in the address. Both go through the same planner: the same prompt, `PlanSchema` + `prepareOps` validation, one repair round; on repair the previous round's reply is sent back as text. JSON extraction tolerates one more case: when parsing the whole text fails, it takes from the first `{` to the last `}` (non-Claude models often add a sentence before or after, and it applies to Claude too); `<think>…</think>` in the reply is removed; `finish_reason: content_filter` or a `refusal` field counts as a refusal. "Test connection" uses `GET {Base URL}/models` (costs no tokens), and if the entered model is not in the list it reports not found (a loose comparison of the `models/` prefix and `:latest`). **Security**: the two keys are stored separately in secure storage and the interface shows only the last four characters; the Anthropic key is sent only to api.anthropic.com, so switching provider never sends it elsewhere; the OpenAI-compatible key is sent only to the saved address, the address must be saved before the key can be entered, and changing the address deletes the key; the address must be https, with http allowed only for localhost / 127.x / [::1] (LAN http see P-042); errors carry only the status code and category, not the provider's original text. "Settings → AI" states which host the request goes to and that what is sent is the interface config and the user's words (no files or entries); when the OpenAI-compatible API is selected it says that only Claude has been tested and other models are more likely to misunderstand or refuse; error copy does not name Claude. The official relay server (`apps/api`) is unchanged and still uses only Claude

**Why:** The founder decided on 2026-10-26 (before promotion; the most common criticism in the open-source community is that only closed-source Claude can be used). One OpenAI-compatible transport layer covers most providers and local models without connecting them one by one; validation is in the App, so a weaker model only gets refused more often and never gets a wrong change applied

**Status:** Decided

### D-242 — Filter files by condition

A new `file.filter` action keeps only files that meet every chosen condition: type, size, landscape, portrait or square, date period, or duration. It only leaves files out of the run and never deletes them. If nothing matches, the run stops and explains, or passes everything on, as chosen. Conditions are fixed choices and numbers, not expressions.

**Why:** Needs such as "only photos from the last 7 days" or "skip files that are too big" could not be done before.

**Status:** Decided

### D-243 — One output per group

`pdf.fromImages`, `pdf.merge` and `zip.create` can produce one output per group: by a fixed count, by day, or by month. Groups run from earliest to latest, named by date, and files with no readable date go in a last "No date" group. Grouping happens only at the step that turns files into files, so later steps are unchanged.

**Why:** Running the following steps per group would act like a loop, which the executor and the AI could more easily get wrong.

**Status:** Decided

### D-244 — Name with recognized text

`file.rename` can name files from text recognized on the device (`{ocr:rule}`) or a QR code (`{qr:rule}`), using fixed rules only, and the text is not kept or sent to the AI. The founder decided on 2026-10-28 that the same rules may prefill a new entry, which D-394 limits to suggestions.

**Why:** Naming receipts and invoices by number or date was a common need that had to be typed by hand.

**Status:** Decided

### D-245 — Text processing

The text tool gets four actions: tidy blank lines and spaces; replace one word with another, with both words kept private from the AI; extract phone numbers, emails, links, numbers or dates, one per line; and split or join lines with a chosen separator. Only fixed operations are offered, with no regular expressions.

**Why:** After OCR, speech-to-text or translation, text often needs cleaning or contact details pulled out by hand.

**Status:** Decided

### D-246 — Conditions in formulas

`core/formula.ts` (D-188) gets one new node, `if(left operator right, when true, when false)`. The only operators are `> < >= <= =` (`≥ ≤` and the Chinese comma are also accepted). A comparison can only be written as the first argument of `if`; there is no and / or, no text comparison and no other functions (for several conditions, nest `if`). An `if` counts as one level of parentheses; the limits of 20 nesting levels and 200 characters (500 characters since D-281) are unchanged, and the formula is still parsed into a small tree and then evaluated. If either side of the comparison has no value, the whole formula has no value; the branch that was not selected may be empty without effect. Equality allows a relative error of 1e-9 (0.1 + 0.2 = 0.3). Prompt rule 32

**Why:** The founder asked for it in the task brief of a cloud session on 2026-10-26 (this changes D-188's "no conditional branches"). Calculations such as "10% off at 100 or more" or "rating of 5 stars adds 50" used to need a separate field filled in by hand. Only one fixed-shape condition is added, not an expression language: no variables, loops or custom functions, consistent with D-188's boundary

**Status:** Decided

### D-247 — Dates in formulas

The founder asked for this on 2026-10-26. Formulas can use date fields of the same table, plus `today` and `days(from, to)` for the whole days between two dates. **Why:** Asking how many days remain until a due date is a common need.

**Status:** Decided

### D-274 — Scan flattening (UVDoc + refinement by text line)

`scan.detect` gets a parameter `flatten` (omitted or true both mean on; the switch is "Flatten curved pages"; the built-in scan quick action writes `flatten: true`, old configs need no migration). After straightening (pages from the document camera too): pad the border with dark edges of 6% of the long side, scale to 488×712 and feed it to the UVDoc grid model (fp16, outputs only a 45×31 warp grid; the new native function `modelRun` runs it with ONNX Runtime, tensors go through temp files). When the text recognition model (`ppocr`) is installed, render a small image with a long side of 1280 according to UVDoc, use PP-OCRv6 det to find text lines, then find table lines: whole-page deskew (long lines and horizontal table lines take a length-weighted median, limited to ±0.5°, no rotation under 0.1°, no rotation when there is only one vertical line) + line-by-line straightening (sliding median + Gaussian smoothing, clamped after smoothing to within 2% of the long side, no refinement with fewer than 5 lines, vertical lines are also straightened when there are two or more); without `ppocr` it only flattens. The UVDoc grid, rotation and shift are combined into one triangle mesh, and Skia `drawVertices` resamples the straightened image only once (`flatten.ts` in `@morph/tool-image`). The model is a separate pack `dewarp` (15.9 MB), kept on our R2 (`morph-tools.stonetech.dev/packs/dewarp/1.0.0/`). License: the model card is Apache-2.0, the UVDoc code and the UVDoc and Doc3D datasets are all MIT, so a commercial app may distribute them, and LICENSE carries all the notices. The manifest uses relative paths and downloads from `EXPO_PUBLIC_MORPH_PACKS_URL`; with no such setting there is no download prompt; with it set, scanning prompts for the download first (the executor's `devicePack` gets `extra`: asked separately from the scan pack); if the user declines, scanning goes on as usual, just without flattening; if flattening fails on a page, that page is not flattened. Recognized text (D-267) therefore uses the image after flattening + refinement and before enhancement. The text-line result is not reused by recognition: recognition is a later step with a long side of 2000, refinement uses 1280, and scanning does not recognize text by default either

**Why:** The founder decided in conversation on 2026-10-29: the most important thing is text-line alignment, and enhancement must not lower recognition accuracy; "Scan" has flattening on by default; the flattening model is its own pack; to be built together with whitening and shadow removal, benchmarked against CamScanner; the model goes on R2 as suggested (the founder replied in conversation, 2026-10-29). Experiment (dewarp-exp in side-session-notes): straightening only gives 2.75% error, straightening + UVDoc 0.04%, CamScanner 0.11%

**Status:** To be verified: unit tests and `npm run check` pass; the same TS ran 19 pages in Node (CanvasKit + onnxruntime-node), line angle spread 0.098° (CamScanner 0.171°). iOS simulator (release build, probe calling native directly): download from R2, straightening, flattening + refinement, enhancement and text recognition all ran through; flattening + refinement takes 0.7–1.4 seconds per page, and pages 17, 1 and 16 had 6 recognition errors (7 after enhancement); the UI was not tapped through. The Android simulator went through the UI (flattening only, about 2.4 seconds), and ONNX Runtime hit SIGILL during refinement (a simulator problem). Not tested on a real device; the download prompt is merged by D-299 with edge detection and recognition into one

**Changed later by:** D-299, D-456.

### D-287 — Lookup field

A lookup shows a value from the record that a reference field points to, such as an hourly rate from a job. ### D-288 — Rollup field

A rollup summarises the records in another table that reference this one: count, sum, average, minimum, maximum, latest value, or streak and day counts. It can be filtered and limited to a period, and the result works in formulas, filters, sorting and stats. With no referencing records, count and sum are 0 and the rest are empty.

**Why:** Habit check-ins, customer orders, monthly spending and stock movements all count records that point at one record; one shared computation serves them.

**Status:** Decided

### D-289 — Previous-entry field

A previous field shows the value of the nearest earlier entry in the same table, optionally within the same group such as a category, ordered by a date. The founder confirmed this on 2026-10-29.

**Why:** Looking at the previous entry needs different settings from a rollup; a separate field keeps the rollup simpler and the AI less likely to mix them up.

**Status:** Decided
