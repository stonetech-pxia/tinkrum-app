# Decisions D-600 to D-619

One heading per decision: what was decided, why, and its status. The exact rules are in the code, its tests and `docs/agent/`. How this log is organized: [DECISIONS.md](../DECISIONS.md).

### D-600 — Whole-data export and restore

On 2026-11-20 the founder chose an explicit whole-data export and restore instead of a backup switch. Settings writes one unencrypted zip of entries, files and app design, and restores only such a zip after the user confirms, with Undo until its banner closes. Not built: a password, scheduled backups, or merging a backup into existing data.

**Why:** With no system backup, a lost or replaced phone would lose everything, so the user keeps an explicit copy under their own control.

**Status:** Decided; not verified on a device

### D-601 — PDF size limit: 100 MB per PDF, 200 MB of PDFs in total per run

The founder chose on 2026-11-20 to raise the PDF limit to 100 MB per file and 200 MB of PDFs per run. Other files keep their own 50 MB and 100 MB totals, counted apart from PDFs. Actions that load a whole PDF into a preview view stay at 50 MB. Not done: a cap on the file-room preview, left to the founder. Changes P-006.

**Status:** Decided

### D-602 — Design suggestions for app files

On 2026-11-20 the founder chose structural design hints for app files, and changed the presets they flagged to match. The checker lists hints after OK, such as a long inline form or a list with no header before the next list; the guide says to apply them unless the person asked for it that way. The import ignores them.

**Why:** Hints written from the principle catch the same mistakes in any AI's file, not only in the presets.

**Status:** Decided

### D-603 — Eight app patterns for other AIs

On 2026-11-20 the founder asked for eight complete app patterns built into Tinkrum, such as a log with totals, a budget against spending, check-ins with streaks and a status pipeline. The guide starts from them, and design hints point to the pattern that shows the fix. Only structure is borrowed from public template galleries, never names or text.

**Why:** Public template galleries show common structures, so other AIs get tested shapes instead of inventing their own.

**Status:** Decided

### D-604 — Tink's feature rules for other AIs, in a file of their own

Rules about Tink's conversation stay out. Changes D-598.

### D-610 — A check-in grid: a record look `grid` and a seventh record tool `remove`

(on 2026-11-20 in conversation the founder asked whether a check-in grid is general enough and fits the kernel, was shown this design, chose "删掉，带撤销" for a tap on a ticked cell, and said "让一个子agent 开工", his yes to this code change). Config: `look: "grid"` with `source.group {by: a link or choice field, showEmpty?, filter? (link only)}` (rows: the same grouping as sections and boards) and a new `source.across {unit: "day" | "week" | "month", by?: a date or datetime field (default the first date field, then the first datetime field), last?: 2–31}` (columns: the chart's time groups, default 7 days, 8 weeks, 6 months, the newest column is the current one, weeks start as `data.calendar` says; only on a grid). A cell is the entries of that row in that column: a filled mark from one entry, the count from two; `show.trailing` (a number field) is summed instead; `show.format {kind: "progress", goal}` draws a ring, the goal a number or a number field of the linked table (each habit's own goal); `show.title` titles the entries listed when a cell is opened. Tools are taps only: one `{as: "tap", do: "create", table, values: "$here"}` (fills the row's option or linked entry, the column's day and the equals of the filter: a date field gets today in the current column and the first day of an older one, a datetime field gets now in the current column and 12:00 of that day otherwise, which no day start (≤6 am) can move; these fields count as filled for required fields) and one `{as: "tap", do: "remove", table}`. A tap on an empty cell adds (no undo banner; a second tap takes it back, invariant 11); with `remove`, a tap on a cell with exactly one entry moves it to Recently deleted (the same soft delete as a user delete, kept 30 days) with an undo banner; a cell with two or more entries is never removed by a tap and lists its entries under the grid, like a calendar day; without `remove` every tap adds one more (counting) and a long press lists the entries. Older cells can be filled in; there are no future columns (paging only goes back, by a whole page). Rows stay pinned on the left; about 7 columns fit and more scroll sideways, opened at the current column. `remove` (record tools go from 6 to 7, relation rule 7 and AGENTS.md updated) is refused everywhere else in this first version: row buttons, button blocks, callouts, a reminder's done, widgets; it writes only the grid's own table (relation rule 12). A new look and keys used only by it: no schema version bump (D-254, D-539); an older app keeps the block as unknown. The founder confirmed it on 2026-11-20 in conversation: "不升，照先例". Tink's rule 68 says when to use it; the habits pattern (D-603) gains a week grid. Invariants touched: none changed; guards added for 11 (remove shows undo, add does not, no setting skips it), 12 (old configs and a saved grid open unchanged), 15 (paging and opening a cell write nothing, grid reading is pure), 17 (a grid writes only its table)

**Why:** Habits, attendance and paid bills are read as rows by days; the tiles show only today, the calendar one series, and back-filling a missed day needed the entry form. One grid over the existing link or choice grouping covers them without a table per habit

**Status:** Implemented; unit tests (core, mobile) and Haiku evals KG43, KG44 pass; seen on the iOS simulator in Chinese and French (adding in a past cell, removing with Undo, a cell with two entries listed, counting with a ring, a datetime column, paging back, 30 rows); the empty state only in unit tests; not seen on a device

### D-616 — Pick several entries of another table, one new entry each: `createAll` with `pick: true`

(asked in conversation on 2026-11-21: the founder approved this code change with "开工" after the design brief: extend createAll rather than add an eighth record tool kind, reuse the `$here` semantics, keep the question, the cap and the batch undo). Config: `{as: "addHere", label?, do: "createAll", table: <the list's table>, from, pick: true, filter?, values}` under a list, cards, checklist, table, gallery, board or calendar. The Add (showing the tool's label when it has one) opens a picker of the entries of `from` (by title, a search box from 9 entries, an empty state that says to add some there first, at most 200 checked), whose button says "Add N entries to “B”"; `filter` limits what can be checked. Each new entry gets `values` (exactly one link field to `from` set to `"$row"`, the picked entry; `{copy}` and dates read it as in D-565) plus the `"$here"` values of D-349: the equals of the list's filter (so on a page for one recipe `recipe is $record` links the recipe) and the section, column or selected day. `values` may not repeat those fields; a required field must come from the filter, `values` or a default. Entries of `from` already linked in that section show as "Already added" and are skipped, checked again at the tap. `$here` rather than `$record` or a new placeholder: the new entries always land in the list the user tapped, it also works off a record page (a calendar day of a meal plan), and the checker can verify it. The picker's button, which says how many and into which table, is the question of invariant 11: tapping it creates them with no second dialog (the founder, in conversation on 2026-11-21: "算，去掉第二次"; the picker's Close is the cancel). Then as D-567: one transaction, at most `MAX_CREATE_ALL`, and the banner's Undo removes the batch. createAll without pick is still refused under a list (it belongs on a button block); pick is refused anywhere but an addHere and must write the list's own table. No schema version bump: an optional key on an existing tool, as D-254 / D-539; an older app refuses such a config instead of misreading it, and no stored data changes. Tink rule 70; agent pattern 9 (recipes, ingredients, recipe items with amounts, a meal plan and this week's shopping list through rollup → lookup → formula → rollup). Invariants touched: none changed; guards added for 9 (no steps or tool reference), 11 (a pick has no setting that skips the question; the picker's button states the count and the table and does not mention undo; tapping it creates with no second dialog and the banner undoes the batch), 15 (checking writes nothing), 17 (writes only the list's table), 18 (deleting the picked table or its link removes the Add, the list stays)

**Why:** A join table that carries data (recipe → ingredients with an amount, order → products with a quantity, outfit → clothes, trip → packing) already worked, but filling it took one form per entry

**Status:** Implemented; unit tests (core, mobile), npm run check and Haiku evals KG45, KG46 pass; seen on the iOS simulator in French and Chinese through a temporary probe, without taps (the simulator panel failed to start): the empty state, already added, checked rows and the button text, the question, the new entries with the Undo banner, the same pick again creating nothing, 250 entries capped at 200; not seen on a device

### D-617 — A checklist's check can also record a date: `also` on `{as: "check"}`

(the founder approved this code change on 2026-11-21 in conversation, answering 「做前三个」 to a list of gaps found by building popular templates as app files with config only; the details were chosen by the implementing agent and not individually confirmed). A checklist's `{as: "check", do: "toggle", table, field}` may carry `also: [{do: "set", field, value}]`, 1–2 fields of this entry, so a tap stays at most 3 writes, all to this entry. Ticking writes the checkbox `true` and the values (`"today"`, `"now"`, an option, a number, `true`, `{from, add, unit}`, `{copy}`; a value read from the entry that is empty is left out); unticking writes `false` and **clears** exactly those fields (clear, not restore: the value before the tick is kept nowhere, invariant 14). Both are one update of the entry with its expected values (`runCheck` → `applyRecordWrites`; nothing is written if it changed meanwhile). No Undo banner: unticking takes back what the tick wrote and ticking again writes it again (invariant 11; the founder confirmed this reading on 2026-11-21 in conversation, answering 「同意，合进 main」 to whether a tick with `also` counts as one simple action that unticking takes back; the wording of invariant 11 is unchanged). One exception keeps invariant 11 exact: when a tick overwrites a value that was already there and different (a date typed in the form), the banner offers Undo once ("Ticked. It replaced a value that was already there."), since unticking can only clear it. Refused with a reason: `create`, `toggle`, `increment` or another table in a check's `also`, a `null` or `false` value (the tick would empty the field and unticking could not bring it back), a required field (unticking would empty it), the checkbox itself. Row buttons with `also` (D-566) and checks without `also` are unchanged. No schema version bump (an optional key that the check already parsed; an older app refuses the config, D-437, D-616). Tink rule 71 (in FEATURE_RULES); rule 62 points a check to it. Invariants touched: none changed; guards added for 11 (at most 3 writes, set only on this entry, no skipping setting, untick returns the entry to its state before the tick, the overwrite case offers Undo; core and mobile)

**Why:** A to-do list wants a real check box that also says when the task was done (a completed date, "done this week"); config could only do it with a "Done" row button (template pattern 16). Clearing on untick is the only reverse that needs no stored copy of the old value

**Status:** Implemented; unit tests (core, mobile), npm run check and Haiku evals KG47, KG48 pass; seen on the iOS simulator through a temporary probe that calls the same action as the check box (not a finger tap): the empty state, entries, a tick showing today as the completed date and counted this week, an untick taking it back, the overwrite case with Undo in French; not seen on a device

### D-621 — A rescue page when Tinkrum cannot open

After two starts in a row that did not reach the home page (a crash, or an error while reading the workspace), the next start shows a rescue page before loading anything of the main app: open as usual, go back to the previous version (each tap one more step, committed as a new version; entries and files untouched), export a backup, check the website, and the version number. An error that stopped the app can be shared from that page only through the system share sheet, when the user taps it; the app sends nothing itself. The start counter is a small file outside the database, cleared once the home page has stayed up for five seconds. The founder chose the share button (decision 6 of the 2026-11-22 health check) and ruled in a Claude Code session on 2026-11-22 that this counter is the app's own bookkeeping, not data, so it does not break invariant 16.

**Why:** a release that crashes at start left users only one way out, uninstalling, which deletes all their data.

**Status:** Decided; not verified on a device

### D-623 — Fill one entry into a user-written template

A user-written template is an ordinary entry in a templates table. A quick action fills one handed entry into text, Word or a draft email on the device, with its output kind fixed in settings; Word preserves the template package and defaults to the template entry's title for its file name. Unknown or ambiguous field-name placeholders stay as written and are reported before continuing. The cloud AI may configure the tables and actions but never sees or writes template content. The founder decided the single-entry scope and fixed output kind in the Claude Code conversation of 2026-11-22, authorized implementation and confirmed the templates-table and default-name proposals in this Codex conversation on 2026-11-23.

The founder kept invariant 19 unchanged and approved the compatible design in this Codex conversation on 2026-11-23: the action accepts records from lists, single-entry containers or `in.records`; when several arrive, the user first selects exactly one. Email opens one draft and returns its filled body as text, so another compatible action may follow. It never fills multiple Word files or emails in a batch. These rules replace the handoff's proposed placement and terminal-email restrictions; they do not create an invariant exception.

**Why:** Existing entry values can fill forms the user already writes without a model reading or composing outgoing text.

**Status:** Provisional; simulator verification deferred by the founder in this Codex conversation on 2026-11-23.

### D-624 — Custom card border and shadow in the theme (`theme.card`)

A theme may carry an optional `card` that describes the card's border (width, colour, opacity) and up to three shadows (offset, blur, colour, opacity, inset) as parameters. Colours are roles of the theme palette (text, primary, secondary, tertiary, border, shadow, white, black), never hex values, so dark mode keeps working with the same parameters. `card` replaces the border and shadow of the named `cardStyle`; the fill still follows `cardStyle` (plain, glass, chrome), and the nine named styles keep their own drawing. Removing it: `setTheme {card: null}`, and a `setTheme` that sets `cardStyle` without `card` also removes it, so picking a named style always shows that style. The founder approved this code change in a Claude Code session on 2026-11-23 ("你推荐的卡片样式改动"); the parameter ranges and role names were chosen by the implementer and not confirmed by him item by item.

**Why:** a new card look needed a new release, and most presets and app files are written by an AI that can only use what the config allows.

**Status:** Provisional; not verified on a device. No invariant touched. The schema version is unchanged: the key is optional, old configs stay valid, and app files that use it list `themeCard` among the features they need.

### D-625 — Icons drawn as path data in the config (`icons`, `my:<id>`)

A workspace config may carry an optional top-level `icons` library: each icon is 1–8 SVG path-data strings on a fixed 24×24 canvas, filled with the even-odd rule or drawn as 2-wide round lines (`stroke: true`), always in one colour taken from where it is used. Only path commands and plain numbers are accepted, checked by a parser in core; full SVG is not. Anywhere an icon goes, `"my:<id>"` refers to one, and every reference must exist (invariant 18), so removing an icon still in use is rejected. Icons are added, replaced and removed through `setTheme {icons}` (no new operation); the library is one per workspace, `preset` and `reset` leave it, and a `setTheme` that only changes icons travels with the function or look change it belongs to. App files carry the icons their content uses, and presets and change history keep them with the whole config. The founder approved this code change in a Claude Code session on 2026-11-23 ("只做svg 路径"); the caps (40 icons, 1500 characters per icon), the id pattern and the `my:` prefix were chosen by the implementer and not confirmed by him item by item. Using a user's own image as an icon was not approved.

**Why:** presets and app files are mostly written by AIs, which could only pick one of the listed icons or an emoji; path data is geometry only, while full SVG can carry scripts and external links that would break invariants 1 and 13 and §3.

**Status:** Provisional; not verified on a device. No invariant wording changed. The schema version is unchanged: the key is optional, and files that use it list `drawnIcons` among the features they need.

### D-628 — A checked file can return through an import link
