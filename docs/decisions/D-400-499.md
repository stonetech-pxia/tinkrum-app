# Decisions D-400 to D-499

One heading per decision: what was decided, why, and its status. The exact rules are in the code, its tests and `docs/agent/`. How this log is organized: [DECISIONS.md](../DECISIONS.md).

### D-400 — The result page's "Save" and a quick action's save step also carry the intermediate format and the original images

When a converted Excel or Word result is saved as a user file, from the save step, the result page or the room, its intermediate format and images are saved beside it, so it can later be opened from Storage and edited. If the intermediate no longer matches the file, only the file is saved. Changes D-367.

**Why:** The founder agreed on 2026-10-30 that an Excel saved outside the room must stay editable, and asked on 2026-11-01 to bring this into main.

**Status:** Decided; not verified on a device

### D-401 — The on-device model is Qwen3.5-2B

Form suggestions combine the code rules with an on-device model, Qwen3.5-2B. The model is asked only about fields the rules are unsure of, one value at a time, and its output is only a suggestion, filled only on a tap. Phones with less than 7 GB of total memory are not offered the download (7 GB is provisional).

**Why:** The founder decided on 2026-11-02, 'go with 2B', and said the model is a product direction for offline and privacy features.

**Status:** Decided; not verified on a device

**Changed later by:** D-404.

### D-402 — The on-device model decides whether to repack weights by total memory

The on-device model repacks its weights on phones with at least 10 GB of total memory, for speed. Below 10 GB, or when total memory cannot be read, it does not repack, which saves memory. The model and the rules are unchanged, and rule suggestions appear at once while the model fills in behind. The 10 GB line is an estimate.

**Why:** The founder decided in conversation on 2026-11-02 to tier this by total memory.

**Status:** Decided; not verified on a device

### D-403 — Prefill rules written into the engine

The date, total, tax and shop-name rules from the research are now fixed code in the prefill engine, with no switch. They only produce suggestions, write no data and use no network. There is no fallback for old receipts, and the date threshold is not relaxed. The tax-word list covers more languages than the research version.

**Why:** The founder decided on 2026-11-02 that these rules go into the prefill tool, with no old-receipt fallback and no regressions allowed.

**Status:** Decided; not verified on a device

### D-404 — When to ask the on-device model (changes the scope of D-401)

This changes the scope of D-401. The model is no longer asked for the shop name when the rules already have a suggestion, and is asked only when the rules have none. The total is still asked unless the first place has at least 3.5 points and leads the second by 1 point. Chinese receipts keep the rules first.

**Why:** The founder decided in conversation on 2026-11-03: keep asking for the total, and ask for the shop name only when there is no suggestion.

**Status:** Decided; not verified on a device

### D-405 — The receipt template's "Category" uses the model to classify when an on-device model is available

The Receipts template gets a single-choice Category field after the amount, with six options: Dining, Grocery and convenience, Drugstore, Other shopping, Transport and Other. The form suggests a category from words printed on the receipt first, and asks the on-device model only when the words are unsure, limited to the table's current options. It affects only newly created tables.

**Why:** The founder said on 2026-11-03 to polish it as much as possible, and to classify with the model when the user can use it.

**Status:** Decided; not verified on a device

### D-406 — The AI entry at the top right of pages

Most pages, including tool and quick-action pages, the record form, the inbox and the file desk, show an AI entry at the top right. Settings, Change history, the AI page and a running run page do not. The entry opens the AI change page for the page it came from, and if the user names another page, that page is changed. Changes D-124.

**Why:** The founder asked for this in conversation on 2026-11-03, and chose these exceptions the same day.

**Status:** Decided; not verified on a device

### D-407 — Planner prompt and validation changes after full testing

The planner prompt gets several rule changes: a part that cannot be done is skipped with a note, one request makes at most 30 operations, undo covers only one step, and ID numbers, phone numbers and addresses stay out of the config. Validation rejects new references that point nowhere, so old configs still open.

**Why:** The founder said on 2026-11-03 to fix the problems found in testing first; several of these choices are provisional and await his confirmation.

**Status:** Provisional

**Changed later by:** D-408.

### D-408 — Invariant 6 changed: text on pages can be written

(the founder, 2026-11-03, in conversation: "As long as it is not sensitive or violating content, users can freely choose the text"; asked whether the AI could write page text directly, he answered "yes"): the AI may write text the user wants placed on a page, blocking only sensitive content (rule 17) and violating content; text sent outside the app (email, posts, replies) still counts as doing things for the user. Replaces the line in D-407 that "text the AI is asked to compose counts as doing things for the user". Saving presets (the founder, same conversation: save the whole app, without records) is recorded separately

**Why:** The user's text is the user's choice

**Status:** Decided

### D-409 — A separate text color for cards, surfaceText

Cards get their own text color, `surfaceText`, separate from the page text color, so a dark page can have light cards with readable text. It equals the text color when omitted, so existing configs look the same. Validation checks each text color against its own background.

**Why:** The founder agreed on 2026-11-03; one text color cannot be legible on both a dark page and a light card at once.

**Status:** Decided

### D-410 — Saving presets

Settings, My presets can save the current app as a preset, without records, and apply, rename or delete it, up to 50 presets. Presets are stored on the device, not in the workspace config, and user-file references are cleared to empty slots when saved or applied. Applying asks for confirmation and can be undone. The AI cannot save or apply presets; it points to Settings.

**Why:** The founder decided on 2026-11-03 to build saving presets. Keeping the preset list out of the config keeps it from going to the cloud AI.

**Status:** Decided

### D-411 — Feature changes spoken in the draft chat box take effect directly (changes D-191)

Feature changes spoken in the draft chat box now take effect directly, instead of being refused, and can be undone in Change history. Any open draft is laid onto the new version and stays open. The reply says the feature is done and that its look part is still in the draft. Changes D-191.

**Why:** The founder agreed on 2026-11-03: a tool is a feature change, and refusing it in a draft fails what the user wants.

**Status:** Decided

**Changed later by:** D-419.

### D-412 — Check inside a round, then fix up

After a plan passes validation, a tool check runs. New problems are sent back to the model once, for a corrected complete plan, with at most three model calls per round. If problems remain, the plan is still shown, with one sentence of reminder in the user's language. A failed correction falls back to the previous valid plan.

**Why:** The founder agreed on 2026-11-03: validation covers legality, but the user wants a tool that works, and the model can fix what it can itself.

**Status:** Decided

### D-413 — When a feature change depends on the draft

Look operations that exist only in the draft are skipped on the official version and redone when the draft is laid on again. If a feature needs a page that exists only in the draft, nothing changes, and the user is offered 'Apply the draft and continue'. The founder confirmed this direction in conversation on 2026-11-03.

**Why:** Operations legal on the draft but not applicable to the official version made up 4% of rounds in real tests.

**Status:** Decided

### D-414 — The tool list (changes D-207)

The change page keeps a tool list of up to 12 items on the device, across restarts, holding only what the user said and never records. Every AI request carries it, and done is judged by code. Widens D-207 from the draft chat box to every request. The founder confirmed this in conversation on 2026-11-03.

**Status:** Decided

### D-415 — Big jobs broken into steps

A big job becomes a build plan of 2 to 8 steps, which the user sees and can trim before tapping 'Start'. Each step runs its own planner request, with feature changes applied directly and look changes put in the draft. A failed step stops the run, and the user chooses retry, skip or stop. The founder agreed on 2026-11-03.

**Status:** Decided

### D-416 — One "Start" counts as one user action (an interpretation of invariant 16)

One tap on 'Start' counts as one user action, even though each step of a build plan writes a version. Nothing runs without a tap, and a failed step stops the run. A reply that arrives after Stop is not applied. After a restart the app waits at the unfinished step for the user to tap again. The founder already knew this, in conversation on 2026-11-03.

**Status:** Decided

### D-417 — What a preset is

A preset is a set of tools, data structure and look, without records or user files. Tools are file, record or file-into-record kinds, and each must be complete: a file tool needs a connected chain and an entry, and a record tool must say where it records and how it is viewed. The save screen lists up to four problems and offers 'Save anyway'. The founder confirmed this direction on 2026-11-03.

**Status:** Decided

### D-418 — Fix these up

Problems the config already has when a session starts are not counted, so only problems added during the session show. A 'Fix these up' button sends one AI request with a list of up to 10 problems, and the user sees a sentence in their language. Built-in rules fix only a table with no view and a table with no place to add, and refuse the rest. The founder has not yet confirmed this one by one.

**Status:** Decided

### D-419 — When one plan has both feature and look changes, the look goes directly into a draft (changes this point of D-191, D-411)

When one plan has both a feature change and a look change, the feature takes effect, and the look goes straight into a draft, with no second model call. If the look cannot be applied, the user is told it was not done. Inside a build step the draft is not opened. Changes D-191 and D-411 for mixed plans.

**Why:** A calendar the user asked for was created, but the calendar did not appear while the note said it had; the look was already in the plan, so asking again was unnecessary.

**Status:** Decided

### D-420 — Record notices have a definite duration

ordinary notices disappear after 4 seconds, and tappable ones (the undo for delete, continue the change) after 8 seconds, and not while a finger is held on the button; to get back a deleted record afterwards, go through the trash (D-037)

**Why:** In the walkthrough, "Recorded" stayed for over a minute across pages (invariant 11 unchanged: only delete shows undo)

**Status:** Provisional

### D-421 — Business-card rules and receipt rules are parameters on the table

Each table can be set to receipt or card rules in Settings, Data, and a table with neither uses only the general rules. Receipt and card rules each apply only to their own tables, and card tables skip the on-device model for phone, email, website and address. Existing tables must be set once. The license for the name list awaits the founder.

**Why:** The founder decided on 2026-11-04 that the user knows what a table stores, so the user chooses, and the two rule sets stay apart.

**Status:** Decided; not verified on a device

### D-422 — The text field's `format`: phone, email, website

A text field gets an optional `format` of phone, email or url. Phones and emails then open from the record page's button row with one tap, and websites ask first. The keyboard follows the format, and saving does not check it. Not done: a picker for choosing the format in the app, so only the AI sets it for now.

**Why:** The founder approved this in conversation on 2026-11-04: contacts must be callable with one tap, and no other capability needs touching.

**Status:** Decided; not verified on a device

**Changed later by:** D-423, D-428.

### D-423 — The business-card template, vCard, the buttons at the top of the record page, the QR code in the form

The `business-cards` sample app opens on a contact list. 'My card' is a separate table: it shows its card as a QR code when filled, or lets the user type it in or scan one. A record can be shared as a vCard, and a QR code in a card photo pre-fills the new-record form. The vCard leaves out photos, notes and groups. (The founder, 2026-11-04.) Changes D-422.

**Why:** A business card should be saved with one scan, called with one tap, and exchanged with any other app.

**Status:** Decided; not verified on a device

**Changed later by:** D-428, D-434.

### D-424 — Search, switchable sorting and grouping on lists, shown by whether the table has records; the single-record block

Lists can search, sort and group by a field, all switchable on the page and not saved, so leaving the page resets them. Search reads the whole table, ignores case and width, and needs every word to match. A new `showIf` condition draws a block only when a table has records. A new `single` block shows the earliest record of a table, with an optional QR code.

**Why:** The founder decided on 2026-11-04 that switching is not saved and writes nothing; the business-card template needs these three.

**Status:** Decided; not verified on a device

**Changed later by:** D-431.

### D-425 — Reports can carry attachments

Printing a report can add each record's photos and attached PDF pages after the report, one per page, headed with the record's title and printed values. Limits: 60 attachments and 40 MB in all, and unreadable or oversized ones are skipped and noted in the report, so the whole report still prints. The Expense assistant sample app turns this on.

**Why:** The founder approved this in conversation on 2026-11-04: expenses must be submitted with their receipts.

**Status:** Provisional

### D-426 — Ask before saving a new record whether there is an identical one

Before a new record is saved, a dialog names an existing record that matches: same amount and date with the same merchant (when both have one), or the same phone or email on a business card. The user can save anyway or go back to the form. Nothing is merged or deleted, and the check runs only on tables with rules.

**Why:** The founder approved this in conversation on 2026-11-04, because scanning easily records the same receipt or card twice.

**Status:** Provisional

### D-427 — Records to Excel

Records can be exported to one Excel file named after the table, with the same columns as CSV. Amounts and dates are real numbers and dates, and text is never a formula. The Expense assistant sample app gets an export button, and leaving the app still needs the user's own share tap.

**Why:** The founder approved this in conversation on 2026-11-04; expenses and business cards are both tables people hand to others.

**Status:** Provisional

**Changed later by:** D-new-record-export-templates-1.

### D-428 — Containers hand data to tools

A quick action runs on a record or a list only where the user taps: a table's record-page button row, a list or single-record block, or a list's floating button. Placing one anywhere else, such as reminders or navigation, is rejected. A list hands over all matching records, not just one page. The AI can configure these buttons but cannot run them or see their values. Changes D-423.

**Why:** The founder decided in conversation on 2026-11-04 that the data is already in the container and the tool runs only when the user taps.

**Status:** Decided; not verified on a device

**Changed later by:** D-442, D-new-record-export-templates-1, D-new-record-export-templates-2.

### D-429 — A currency chosen for each entry

An amount field can name a single-choice currency field, so each entry keeps its own currency. Amounts are not converted, and totals show one figure per currency, such as '$100.00 · €50.00'. Things that cannot be added into one number, such as goals or chart averages, are rejected. For now only the AI sets the currency field.

**Why:** The founder approved this in conversation on 2026-11-04: foreign-currency expenses need their own currency recorded, with nothing converted.

**Status:** Decided; not verified on a device

### D-430 — Pinned zones on pages

A page can pin a zone at its top and bottom while the middle scrolls. It is an optional `pin` property on a top-level block, so editing and references work as before. Blocks inside a group, on the file desk, or on a browse list cannot be pinned. The bottom zone sits above the navigation bar.

**Why:** The founder decided this in conversation on 2026-11-04; a contact app should open on a list whose search and actions stay put.

**Status:** Decided; not verified on a device

**Changed later by:** D-481.

### D-431 — List search reads all fields, loads more on scrolling to the bottom, and search can be pinned at the top

List search reads every field of the table, including fields the row does not show, but not attachment contents. Lists with browse load one more page as the user nears the bottom, and changing search, filter, sort or grouping returns to the first page. The search box and its rows can be pinned at the top of the page. Replaces the displayed-text-only search of D-424.

**Why:** The founder decided on 2026-11-04 that a contact list must be searchable by company, phone and notes, and that search should not scroll away.

**Status:** Decided; not verified on a device

### D-432 — The tags field `tags`

Records can carry tags, a set of text values per record, with case-insensitive duplicates removed and at most 20 per record. The config never holds tag names: existing tags are computed from the records, and a tag no record uses disappears. The form types tags and offers existing ones as chips. A config filter on tags can only check empty or not empty.

**Why:** The founder decided on 2026-11-04: users add tags freely, the config never holds them, and the AI cannot see the values.

**Status:** Decided; not verified on a device

### D-433 — Filtering by value on a list, `browse.filter`

A list can filter by up to three tag or single-choice fields, shown as a swipeable row of chips with All plus only the values the list's records use. One value is selected at a time. The selection is temporary, writes nothing, and tags cannot be created from this row.

**Why:** The founder decided on 2026-11-04; finding people by tag is the main use of business cards.

**Status:** Decided; not verified on a device

### D-434 — A separate floating button `dial`, and the business-card sample app now opens on contacts

A new `dial` look is a floating button pinned at the bottom, with one main tool and up to four more that expand into a dimmed row of labeled round buttons. Items can run a tool on the list's currently selected records, open a page, or create an entry. The business-card sample app now opens on contacts, with search and tag filters pinned at the top.

**Why:** The founder decided this on 2026-11-04; the main and expanded buttons form one group, so it is a new look rather than an option on the button.

**Status:** Decided; not verified on a device

**Changed later by:** D-481.

### D-437 — The receipts sample app, viewing the list by this week / this month / this year, and the two buttons pinned at the bottom looking the same

### D-438 — Bar and line charts are now drawn with Victory Native XL

Bar and line charts are now drawn with the Victory Native XL library, pinned to one version so no native rebuild is needed. Tapping, screen-reader labels and readouts still use the original transparent tap layer. Bar charts with negative numbers keep the old drawing. The founder decided this on 2026-11-05.

**Why:** The founder wants charts like Expensify's, and a fuller library is less work than adding axes and gestures on top of Skia.

**Status:** Decided

### D-439 — Charts compared with the previous period, `source.compare: "previous"`

Bar and line charts with time grouping can compare with the previous period, drawn as a gray dashed line or pale gray bars behind the current ones. Pie charts, single-choice grouping and charts with a period filter cannot use it, and the config check rejects them. The founder decided this on 2026-11-05.

**Why:** The founder liked the comparison in Expensify's charts, and it sits in the chart's source, like the number block's compare setting.

**Status:** Decided

### D-440 — Time range on a page: a new look `period`, and `source.period: "page"` for charts and number blocks

The page gets one period selector (today, this week, this month, this year, the last 7, 30, 90 or 365 days, or a custom range) that every chart and number block on the page with a page period follows. The selection is shown only while the page is open and is never written. The founder decided this on 2026-11-05, and Tink can change the options.

**Why:** The founder wants range switching like Expensify's but with only a few options, and one range per page so the numbers and charts agree.

**Status:** Decided

### D-441 — Text to Word: a new action `text.toDocx` (`text` → `files`, tool `text`)

A new text action turns text into a Word file: a blank line starts a new paragraph, and Chinese, Japanese and Korean display correctly. It takes no parameters and does not change records, so a record's text field can be handed straight to it in one step. The founder decided this on 2026-11-05.

**Why:** Converting a record's text to Word is common, and going through PDF and recognition is slow and makes mistakes.

**Status:** Decided

### D-442 — Containers hand attachments to tools: they hand over `files`, and the field type decides what is handed

A record page can hand its attachments to a quick action with one tap, and text-type fields hand over the text they show. Handed files are copied to a temporary run folder, at most 20 at a time, and user files are never touched. A quick action may now start with a files step, which replaces the rule of D-428. The founder decided this on 2026-11-05.

**Why:** Compressing, converting or sharing a record's attachments is the most common need, and it meant choosing the files again.

**Status:** Decided; not verified on a device

### D-443 — "Add an entry" can put into an existing record: `out.addRecord` gains `into: "existing"`

The 'Add an entry' action can now put files and text into an existing record the user picks. The record's form then opens so the user checks it and taps Save; content is appended and nothing is replaced or deleted. Putting into several records at once and writing back to the source are not done. The founder decided this on 2026-11-05.

**Why:** After processing a record's attachments, they often need to go into another record, and before they could only go into a new one.

**Status:** Decided; not verified on a device

### D-444 — Creating a new form after importing a file

After a file is imported, the inbox's Save as an entry starts with a New form page. It begins as Blank and lists presets ranked by rules, and an on-device model picks one only on a tap. Fields are found by layout and filled only on a tap, and the table is created only when Save is tapped. The founder decided this on 2026-11-05. Changes D-392.

**Changed later by:** D-474, D-476.

**Why:** A table often holds files from different sources where the same information has different labels.

**Status:** Provisional
