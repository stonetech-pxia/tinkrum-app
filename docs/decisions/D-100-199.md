# Decisions D-104 to D-199

One heading per decision: what was decided, why, and its status. The exact rules are in the code, its tests and `docs/agent/`. How this log is organized: [DECISIONS.md](../DECISIONS.md).

### D-104 — First launch preinstalls five tools

A new user's first launch preinstalls five on-device tools (image, PDF, scan, text recognition and QR code), and the navigation bar becomes Home, Tools, AI edit and Settings. Existing users' configs do not change. The founder decided this on 2026-10-23.

**Why:** The first launch must not be empty, and these tools need no download.

**Status:** Decided

### D-105 — Installing and removing tools apply directly, with undo

Installing, adding to the home page, removing from the home page and upgrading in the tool catalog apply directly, with no confirmation dialog; they can be undone from the banner. Uninstalling still asks first (it also removes the tool's workflows)

**Why:** Usability ranking U1: the tools are already in the phone, and an extra "confirm / apply changes" step only makes ordinary people hesitate; undoable operations need no extra question

**Status:** Decided

### D-106 — Applied banner disappears after six seconds

The Applied banner disappears by itself after six seconds, and the change can still be restored from Version history. Warnings about rollbacks, restores and conflicts stay until dismissed. A result smaller than its input shows the before and after size.

**Why:** A lasting banner could make users think Undo reverses the last action, so they uninstall the tool instead.

**Status:** Decided

### D-108 — Run cards on one page show as a two-column tile grid

Two or more run cards on one page show as a two-column grid of small tiles, and tapping a tile starts it, instead of a Start button on each card. A single card keeps its full layout. Only the display changes; the AI and edit mode still see individual components. The founder decided this on 2026-10-23.

**Why:** The image tool has more than a dozen features, and the page was hard to scan.

**Status:** Decided

### D-109 — New AI workflows offer a home-page shortcut checkbox

When the AI creates a workflow with no page entry, the preview adds a checkbox, Add a shortcut on the home page, checked by default unless the user said not to. If the user asked for the home page, the card is added directly without the checkbox. After applying, the user is taken to the new workflow or the changed page.

**Why:** The founder chose this option on 2026-10-23: new things must be findable, but the home page must not change without the user knowing.

**Status:** Decided

**Changed later by:** D-190.

### D-110 — AI builds the doable part of goal-style requests

The AI builds the doable part of goal-style requests, adds steps according to purpose, and skips steps the goal does not need. It shows short notes on what cannot be done, such as scheduled runs, and no longer adds home-page cards on its own. Not done: asking one question first, which needs a protocol change.

**Why:** The AI added a home card every time and never explained limits, so the founder chose this group first on 2026-10-23.

**Status:** Decided

### D-111 — Pop-up pages get a Close button at top left

Pop-up pages for AI edit, run and record get a Close button at top left, so users need not know to swipe down. On the run result page Done is primary, Run again secondary, and Edit workflow a small link. Wording changes wait for the founder's decision.

**Why:** Ordinary people do not know to swipe down to close, and Edit workflow beside Run again is too prominent.

**Status:** Decided

**Changed later by:** D-362.

### D-112 — UI wording switches to everyday terms

The UI wording is changed throughout to everyday language (only text the user can see; identifiers such as workflow, pack and install in code, and the engineering docs, do not change): workflow → **Quick actions** (not Shortcuts, to avoid clashing with Apple's Shortcuts); pack → called **Downloads** in Settings, with the prompt "Needs a one-time download of X MB the first time, then works offline" the first time it is used, the word appearing nowhere else, and the word "pack" also dropped from download item names; install / uninstall / installed → **Add / Remove / Added**; apply changes → **Make this change**; before / after the change → **Now / After**; version history → **Change history** (navigation bar label Changes), with entries shown as "Today 13:51 · By you": the number and seconds are dropped, "manual change / AI change" becomes "By you / By AI", and dates are shown as today, yesterday or a specific date; restore this version → **Go back to this** (the record after a restore reads "Went back to X"); component → **block**, with the edit hint "Tap a block to change it, hold ≡ to drag it to a new place, tap 'Done' when finished."; "Edit workflow" on the result page → **Adjust settings**. The banner's "Applied" → **Changed**. The plan descriptions generated by the core, refusal messages, banners and AI page examples change together. The offline rules and the planner recognize both old and new wording (planner rule 23: text shown to the user uses only the new wording); the eval adds QA1–QA6

**Why:** Founder decided on 2026-10-23 ("change the wording as you recommend", usability ranking U5): ordinary people do not understand engineering terms like "workflow", "pack" and "version #3"

**Status:** Decided

### D-113 — Product principle: the AI only changes the app, it does not do things for the user

When the user states a thing to get done (for example "compress my photos to 200KB", "front and back of my ID, the school wants one PDF"), the AI's response is to build in the app a quick action (or page) that can be used again and again, going through the usual preview → Make this change → undoable; after applying, the user is taken to that quick action and taps "Start" himself. The AI does not: run the quick action itself; produce a one-off result (write an email, answer a question, summarize a file's contents); or hold a multi-turn chat with the user. If "ask first when unsure" is added later, it is only one question before the change. Use this rule to judge any new AI feature from now on

**Why:** The founder worried on 2026-10-23 that "AI just does it for you" would turn Morph into an AI personal assistant, competing head-on with general assistants and losing the difference of "stays and fits better the more you use it". Turning task-style requests into quick actions gets the job done the first time and makes it one tap later

**Status:** Decided

**Changed later by:** D-396.

### D-114 — Share to Morph

Photos and files shared from other apps reach Morph through a share extension on iOS and a share intent on Android. Only images and files are accepted, up to 50 at a time; text and URLs are rejected. Nothing happens in Expo Go or in tests, where the native module is absent.

**Why:** A maintained, license-compatible library is ready, and writing our own would mean maintaining the code that generates the Xcode target.

**Status:** Decided

### D-115 — Shared files feed only the first step of a workflow

Shared-in files feed only the first step of a workflow, when that step takes photos or files, replacing the picker for that run. No new action is added, and the usual type, count and size checks apply. The first step's ask-every-run is skipped.

**Why:** Existing workflows, presets and self-built ones take a share without any change.

**Status:** Decided

### D-116 — Shared files are deleted when the inbox is closed

Shared files are held in memory as a batch, not in the config, and are deleted when the inbox closes or another batch arrives. A run copies them to its own temporary folder, which is removed when the run page closes. Only files with generated names are deleted; Android content addresses are neither copied nor deleted.

**Why:** The system does not clean up the shared folder, so Morph must delete the files it received.

**Status:** Decided

### D-117 — Inbox page lists choices and never runs anything itself

Updated by D-208 and D-361: the save-to-files option was removed and Put on the desk is the first item. The inbox lists the received files and the workflows that accept them, the user's own first. Workflows with the wrong file count are listed with the reason but cannot run, and nothing runs automatically.

**Why:** Users sharing often have not decided what to do yet, so choices come first, and the reason shows why a workflow cannot run.

**Status:** Decided

**Changed later by:** D-361.

### D-118 — Own share controller replaces the generated one

The iOS share extension uses Morph's own controller, which copies each shared file in order and hands over to the app only after all are copied. It shows no UI and uses no network. It replaces the generated controller until the library's concurrency problem is fixed.

**Why:** The generated controller handed over early and dropped files when two PDFs were shared.

**Status:** Decided

### D-119 — Share several files at once

Several files can be shared at once. On both platforms the app uses the system share sheet with all files in one call; Android hands out read-only content addresses to the app the user picks. Sharing a single file and CSV export still use the simpler path.

**Why:** The system share sheet covers what is needed, while a third-party library adds social-app connections and no folder saving.

**Status:** Decided

### D-120 — Save to a folder chosen in Files

A new action saves outputs into a folder the user chooses in Files, and the result page gets a Save to folder button. Duplicate names are numbered, and closing the picker is not a failure. If the folder cannot be written, the app says so and asks for another folder.

**Status:** Decided

### D-121 — Not done

Not done: calling cloud-drive APIs to upload directly, and sending files to chat contacts automatically. Cloud drives are reached through their own apps' Files providers, and chat apps are chosen by the user in the share sheet, so Morph itself does not upload or use the network.

**Status:** Decided

### D-122 — Presets ending in share become one share of all files

Presets keep their steps: presets that end with `out.share` (photos by email, document bundle, sign and return a form, scan document, merge several documents into one, screenshot redaction and sharing, send photos in batch) automatically become one share of all the files. "Send photos in batch" keeps the ZIP packing (P-018 decided)

### D-123 — Remember the last chosen folder

The whole app remembers one save folder. Once chosen, Save to folder writes into it without the picker, and Change folder picks and remembers a new one. Morph only creates new files there and never reads or changes existing ones. The folder name is shown only on the device. The founder decided this on 2026-10-23. Changes P-019.

**Status:** Decided

**Changed later by:** D-196.

### D-124 — AI changes record where they were opened from

An AI change now records where it was opened from: a quick action (only its id) or the inbox page (only the counts of photos, PDFs and other shared files). The AI never receives file names or contents, and the screen shows what is being changed. A change from the inbox must give the new quick action a first step that accepts those files.

**Why:** People ask for 'make it smaller' or 'make it one PDF' without naming anything, so the context must come from where they tapped.

**Status:** Decided

**Changed later by:** D-406.

### D-125 — "Quick action is ready" page

After an AI change creates one quick action, a ready page shows its name, steps and where it is found, with 'Use it once now' (the user starts it on the run page), 'Not now', and 'Ask the AI to change this'. Several new quick actions at once still use the earlier list. The Run button for added ready-made actions was cancelled by D-236.

**Why:** The founder agreed on 2026-10-23: the job gets done the first time, and what stays behind is a reusable quick action that the AI does not run for the user.

**Status:** Decided

### D-126 — "Ask the AI to change this"

The result page and the ready page offer 'Ask the AI to change this', which changes the quick action itself with the usual preview, confirmation and undo. Afterwards it returns to the result page, and 'Run again' uses the changed steps.

**Why:** The founder agreed on 2026-10-23: saying 'a bit smaller' is easier than describing everything again, and what changes is always the app.

**Status:** Decided

### D-127 — Suggestions from usage habits

When the same answer is given three times in a row to a quick action that asks each time, the result page suggests making it a quick action on the home page. 'Make one' is a single undoable change, and 'No thanks' stops the suggestion. Only numbers, options and switches are counted, and the counts stay on the device.

**Why:** The founder agreed on 2026-10-23: habits settle into the app, but it changes only after a tap, and counting needs no AI.

**Status:** Decided

**Changed later by:** D-362.

### D-128 — Errand requests

Errands, such as writing text, answering questions, translating or summarizing file contents, looking things up, sending something by itself, or running a quick action now, are refused in one sentence saying Morph only changes this app. The refusal gives examples of related quick actions that could be built. File goals such as compressing photos are still built as quick actions.

**Why:** The founder agreed on 2026-10-23: every refusal also explains what Morph is for.

**Status:** Decided

**Changed later by:** D-171.

### D-129 — Build one on the spot in the inbox page

In the inbox, the order is: the user's own quick actions, 'Ask the AI to build one', ready-made ones whose first step accepts these files, then single tool features. A new one is shown first, marked 'Just made', and the user still taps Run. D-208 changed the inbox order, and D-236 changed 'Add and run' to 'Run'.

**Why:** The founder agreed on 2026-10-23: when sharing there is often no suitable quick action, and next time the same kind of file is shared the new one can be used at once.

**Status:** Decided

### D-130 — Ready-made quick actions are grouped by life scenario

Ready-made quick actions are grouped by life scenario: getting documents abroad, handing in materials and signing files, expenses and bookkeeping, and sending photos. The quick actions page shows these groups in that order, and each ready-made action belongs to exactly one group.

**Why:** The founder agreed on 2026-10-23: many people cannot say what they want, but recognize it when they see the scenario.

**Status:** Decided

### D-131 — The planning service is deployed on the founder's Mac mini

The planning service runs on the founder's Mac mini from a separate production copy, kept running by launchd and reached through a Cloudflare named tunnel, so no router port is opened. When the machine is off, the app says 'Can't reach the AI service right now' and changes nothing. The plan is to move to cloud hosting when there are more users. Deployment steps are in the deploy guide.

**Why:** The founder decided on 2026-10-23: early requests are few, so hosting costs nothing, and the tunnel exposes neither an open port nor the home IP.

**Status:** Decided

### D-132 — Temporary protection until login ships

the app carries a client token baked into the build (`x-morph-client`; the server's `MORPH_CLIENT_TOKEN`; a mismatch returns 401) and a random device id generated on first use (`x-morph-device`, kept in secure storage). Limits are now per device: 10 per minute and 50 per day; there is also a cap of 500 per day across all devices (`MORPH_GLOBAL_DAILY_LIMIT`). Counts are in memory and reset when the service restarts

**Why:** The founder chose this on 2026-10-23 (the Supabase login in CLOUD_DESIGN is not built yet). The token can be extracted from the install package and the device id can be forged, so the real backstops are the global cap and the monthly spend limit in the Anthropic console; what they stop is someone who stumbles on the endpoint and hammers it. Once the Supabase JWT is connected, remove the token and meter per user (CLOUD_DESIGN §7)

**Status:** Decided

### D-140 — Value types `video` and `audio`

The founder decided on 2026-10-23 that video and audio become kinds of file with a shared duration. They were designed together, but this batch implements only video and PDF compression, and audio follows later. The PDF merge action refuses video and audio, and the validator and the Add a step button both check this. The schema version goes from 6 to 7, with a migration that only changes the number.

**Why:** Video is often several GB and cannot be read whole into memory the way a PDF can, so it needs its own handling.

**Status:** Decided

### D-141 — Processing video on the device: a local Expo module, `modules/morph-media`

Video is processed on the device by a local native module, with AVFoundation on iOS and Jetpack Media3 on Android, behind one interface. The founder agreed to option A on 2026-10-23. Expo Go has no such module, so there video actions need the full app. Other libraries were rejected for licensing, speed, or missing trimming and target-size control.

**Why:** System frameworks use hardware encoders, which are fast, save battery, give precise bitrate control, and have licenses compatible with AGPL.

**Status:** Decided

### D-142 — Video input and size

The founder decided on 2026-10-23 that users can pick one to ten videos from the photo library or from Files. Morph does not record video. Videos are streamed, so the 50 MB limit for other files does not apply; each is at most 4 GB, and the phone's free space is checked first. Large files are moved, not copied, into the run's temporary folder. Changes P-006.

**Why:** An ordinary video is often hundreds of MB, and copying it would double the storage it takes.

**Status:** Decided

### D-143 — Video actions

There are three video actions: compress to a target size in MB or to 1080p, 720p or 480p; convert to MP4; and trim a segment without re-encoding. The output is always MP4 with H.264 and AAC, with no HEVC option, as the founder decided on 2026-10-23. A target that the video cannot reach is refused before starting, with the minimum size shown.

**Why:** People say it cannot be sent or must be under 25 MB, and MP4 with H.264 plays everywhere.

**Status:** Decided

### D-144 — Share video and audio into Morph

Morph also accepts videos and audio files from the share sheet, on Android and on iOS. The inbox shows duration and size for them, with the same size limit as videos picked in the app. Shared video goes into the video input action, and a future audio input can connect the same way. Changes P-017.

**Why:** Android did not accept video or audio at first, because no action could process them.

**Status:** Decided

### D-145 — Compress PDF

A PDF compress action first recompresses only the images, keeping text, links and forms. If the target still cannot be reached, a setting decides: ask the user (the default), convert pages to images, or keep text. Converting to images makes text unselectable, so the user is asked first. Password-protected files still fail. The founder agreed to option C on 2026-10-23.

**Why:** A PDF that will not upload is usually a phone scan, and recompressing its images is often enough.

**Status:** Decided

### D-146 — Where it goes

The founder decided on 2026-10-23 that the Video tool is preinstalled for new users, with compress, convert to MP4 and trim. The PDF tool gains Compress PDF, which existing users get by tapping Update. Two ready-made quick actions are added: Video too big to send (default 20 MB) and PDF too big to upload (default 2 MB).

**Why:** These two are the most common problems ordinary people have with files.

**Status:** Decided

### D-147 — The AI knows video and PDF compression

The AI maps requests to the new actions: too-big video to compress, format changes to convert, trimming to trim, and an existing PDF is compressed directly rather than converted to images and back. Shared videos and audio use the matching input. Built-in phrasings cover common wording, and 'compress to N MB' picks the action from the kind of file in the previous step.

**Why:** 'Compress this video to 20MB' is a goal, so it becomes a quick action like other file goals rather than a refusal.

**Status:** Decided

### D-150 — Speech to text (iOS) uses the system Speech framework and recognizes only on the device

Speech to text on iOS uses the system speech framework and works only on the device, in 12 languages, with Mandarin split into Simplified and Traditional. Newer systems use the newer system analyzer, while older systems and unsupported languages fall back to the older recognizer. If a language must be downloaded first, the app asks the user before downloading. Results are not sent to the AI.

**Status:** Decided

### D-151 — Speech to text (Android) compiles whisper.cpp v1.9.5 (MIT) into the app, and the models are downloaded content

On Android, speech to text runs whisper.cpp compiled into the app, with two downloaded model sizes (small and base) plus a voice-activity model. Mandarin gets a Simplified Chinese prompt. Downloaded files over 32 MB have their SHA-256 checked while being read. The default model choice still awaits the founder.

**Status:** Decided

### D-152 — Audio tool

A new audio tool offers speech to text, making audio smaller, converting between M4A and WAV, trimming a segment, merging recordings in order, and taking the sound from a video. Encoding uses the native video module and recognition uses the speech module. The tool is not preinstalled.

**Status:** Decided

### D-153 — Audio bitrate

(`core/audio.ts`): by size = target × 8 × 0.94 ÷ duration, at most 192 kbps, stereo only at 96 kbps and above, 22.05 kHz at 48 and below, below 24 kbps it reports `audioTooSmall` (with "at least X MB"), and if over target it recompresses in proportion, at most 2 times; by quality high 192 / standard 128 / voice 48 mono, never higher than the original; converting format follows the original bitrate (×1.2, 48–192). No MP3 (open, P-020)

### D-154 — Pick audio / record

Audio can be picked from Files, or recorded in a built-in recording screen that keeps recording with the screen locked. A recording shared into Morph fills the first step directly. If the phone has no microphone, the recording screen says so in one sentence.

**Status:** Decided

**Changed later by:** D-653.

### D-155 — Trim a segment and merge

trimming re-encodes to M4A (any format can be trimmed, accurate to the millisecond), and the screen uses a native waveform (120 bars, read after the screen opens: on Android a 10-minute recording takes about 1 minute to decode) and states the ringtone situation: on Android it can be chosen in system settings, on iPhone the app cannot set it; merging joins them end to end in the current order, and the file is named "first segment and N more"

### D-156 — Ready-made quick actions

(D-130's new scenarios): "Study and work": recording to text, merge several recordings into one, voice memo filed by date; "Send audio": voice too big to send, trim an audio clip, save the sound of a video. The group names await the founder (P-021), and the preset name "Trim an audio clip" avoids clashing with the video tool's "Trim a segment"

prompt rule 20 gains the audio wording, rule 24 "turn the recording into text" is a goal while "summarize what the recording says" is doing a chore for the user, and rule 25 shared audio uses `in.audio`; mock phrasing AU (MOCK_AI_PHRASES); eval AU1–AU7 (built-in rules) and PAU1–PAU6, SH4 (real model). ### D-160 — Long tasks continue when switching to another app (Android)

On Android, a run with video or audio steps keeps going in the background through a foreground service that shows one notification with the current step and percent progress, and it keeps running with the screen locked. The whole run is kept alive, including saving. The notification has no Stop button, and swiping Morph away stops it. On Android 15 the service stops after six hours in 24. The founder chose option 2 on 2026-10-24.

**Why:** Transcribing an hour of audio can take half an hour on a real phone, so users cannot be asked to stay in the app.

**Status:** Decided

### D-161 — Notification permission is asked only once

(from Android 13): the first time a quick action with a long step runs, the system notification permission dialog appears; if refused, the task still finishes in the background (only the progress is not visible in the notification bar), and it is not asked again (the native module records in SharedPreferences that it asked)

**Why:** Not allowing notifications does not affect background continuation, so there is no need to bother the user repeatedly

**Status:** Decided

### D-162 — Completion notification

when a long task ends, one is sent only if Morph is not in the foreground (success "'X' is done · tap here to see the result", failure "'X' did not finish · tap here to see what happened"); none if the user stopped it themselves; one tap returns to the result page. Two notification channels: "In progress" (low interruption) and "Done"

**Why:** A reminder is needed only when the user has switched away; in the app they see the result page directly

**Status:** Decided

### D-163 — iOS 26 background tasks (BGContinuedProcessingTask) are turned on

(`continuedProcessingEnabled = true` in `MorphBackgroundModule.swift`; confirmed by the founder on a real iPhone on 2026-10-31: while compressing a video he switched to the home screen, the system showed progress, and it was already done when he came back): the task is submitted when the run starts, the system shows progress, switching to the background while morph-media holds the task does not count as an interruption, and when the system takes the time back it ends with `interrupted`. Below iOS 26 it is the same as D-148. **The simulator does not support background tasks** (submitting reports "BGTaskScheduler is not available on this platform", treated as unsupported on the simulator), and the simulator does not suspend an app that was switched away from, so this can only be confirmed on a real device; see MVP_SCOPE "Long tasks continue in background"

**Why:** Whether the video encoder and speech recognition can be used in the background is decided only by a real device (the simulator's encoder differs from a real device's; some developers say the iPhone cannot get background GPU)

**Status:** Decided

A new translation tool translates text, with the source auto-detected or one of 20 languages and the target asked at each run. The founder started this work on 2026-10-23.

Translating a file, such as a contract or a screenshot, becomes a translation quick action: get the text, translate, then copy, lay out as PDF, save as text or share. Translating a sentence the user types is still refused as an errand, with examples of translation quick actions instead. This changes the boundary of D-128. ### D-172 — Plain text output only, no translation that keeps the original layout

Translation returns plain text that can be copied, saved as a text file or laid out as a plain-text PDF; tables, images and layout are not kept. The app says in three places that on-device translation is for understanding meaning, and official documents need a professional translator. The founder has not yet confirmed this; the default applies meanwhile.

**Why:** Keeping the layout means locating and refilling each block, which is much more work and more error-prone; on-device quality suits understanding rather than submission.

**Status:** Awaiting the founder

### D-173 — 4 translation ready-made quick actions

Four translation ready-made quick actions are added under the existing scenarios: a foreign-language PDF to Chinese, photographed foreign documents to Chinese, Chinese documents to English, and screenshot translation under sending photos. A quick action's first step takes only one kind of input, so one planned preset was split in two. The split and the screenshot placement are judgment calls made in this session.

**Why:** Chaining recognize, translate and save or send lets ordinary people find it by their situation.

**Status:** Decided

### D-174 — Translation phrasings of the built-in rules (mock)

Built-in phrasings recognize 'translate into X', plain 'translate' (asks each time), enter or paste text, extract PDF text, copy text and save as a text file. Asking to translate a whole file creates a translation quick action, and asking how to say a phrase in English counts as an errand. Follow-up steps swap to fit the previous one, so extract text after a PDF means extract PDF text.

**Why:** The mock must match the real model's boundary, and the examples in a refusal must point to changes that can really be made.

**Status:** Decided

### D-175 — Downloading translation languages

On Android, when a run reaches translation, Morph first checks which needed languages are missing and asks once for all of them, with the approximate download size; the download starts only after the user taps Download. With no network it stops at once with a clear message. Downloaded languages can be deleted in Settings. On iOS the system shows its own download prompt.

**Why:** It matches the existing download experience, and neither ML Kit nor Apple lets the app control the download address.

**Status:** Decided

### D-176 — Splitting before and after translation

Text is split into paragraphs before translation and joined back afterwards, so lines broken by text recognition or PDFs do not split a sentence. With auto-detection, each paragraph's language is detected separately, and paragraphs already in the target language are left as they are. Text longer than 100,000 characters is refused as too long.

**Why:** Recognition and PDFs break lines by layout, and bilingual material is common, so whole paragraphs with their own detected language give better results.

**Status:** Decided

### D-177 — Downloading new tools from the server

New tools can be downloaded without an app update, but only tools the team writes, tests and signs; no third-party code and nothing generated by the AI on the spot. Anything needing system capabilities, such as video, OCR or native libraries, still ships with the app. The first step delivers data tools only; plugin tools with new actions come in a second step. (The founder, 2026-10-23.)

**Why:** The store rules allow downloaded mini-programs but not exposing system interfaces to them, so system capabilities must ship with the app.

**Status:** Decided

### D-178 — Details of downloading new tools

Tool packages and a signed catalog are hosted on Cloudflare R2 and signed with the founder's Ed25519 key, which stays in a password manager and is never written to a file. The founder chose this on 2026-10-24. The app holds two public keys to allow rotation. Revocations apply once the device is online, updates are tapped by the user, and downgrades are not allowed. Plugins cannot call native capabilities; they are chained with built-in actions in a quick action.

**Why:** Content is signed, so the host need not be trusted; a private key kept on an online machine would let an attacker push code to all users.

**Status:** Decided

### D-179 — Implementation of step one of tool downloads

Step one of tool downloads is built for data tools: a downloaded tool holds text and quick actions, with its page laid out like the built-in small tools. The app registers downloaded tools at launch, before opening the workspace, and the planning service pulls the catalog every 15 minutes. The official public keys were added on 2026-10-24; the storage bucket is not yet created.

**Why:** It looks the same as built-in tools, and the page layout does not have to be stored in the tool's manifest.

**Status:** Decided

### D-181 — The toolbox is a page the AI can change

The toolbox is an ordinary page the AI and users can edit: a grid of tool icons, three per row, grouped by purpose (photos and video, files and documents, text, more tools) with a Manage tools button. Tapping a tool not yet added adds it at once and opens it. Tools on no grid appear under More tools. The founder chose this layout on 2026-10-24 and asked that the AI be able to edit it; the group names are defaults.

**Why:** A grid takes less room than a list of bars, and as an ordinary page the AI and edit mode can both change it.

**Status:** Decided

**Changed later by:** D-645.

### D-182 — Slimmed-down home page for new users

New users get a slimmed-down home page: a title and a 2x2 set of tiles with three ready-made quick actions (video too big to send, photos by email or upload, PDF too big to upload) and a Toolbox entry. The bottom bar holds only Home, AI changes and Settings. Existing users are not changed. The home layout was later superseded by D-223 and then by D-231. (The founder, 2026-10-24.)

**Why:** Tools that fix one problem, such as convert or compress, are downloaded far more than toolbox apps, so the first screen offers what works right away.

**Status:** Decided

**Changed later by:** D-223, D-231.

### D-183 — MP3 output

MP3 output is added to audio format conversion and to extracting sound from video, using the LAME encoder (LGPL) built from source included in the repository. Quality is fixed; the bitrate is 1.5 times the original, rounded to a standard tier from 128 to 320 kbps, and mono stays mono. Merging and trimming still output M4A only. This overturns P-020.

**Why:** The founder asked on 2026-10-24 to fill the format-conversion gap; LGPL fits with AGPL when all source is published, and MP3 patents expired in 2017.

**Status:** Decided

### D-184 — Animated GIF and HEIC to JPG

Video can become an animated GIF, up to 30 seconds (longer clips must be trimmed first), and several images can become one looping GIF of up to 50 images. HEIC to JPG is offered as a separately named, easy-to-find action in the image tool. Android has no system GIF encoder, so Morph includes a small encoder of its own.

**Why:** Video to GIF is in high demand and HEIC to JPG was possible but hard to find; a ready encoder needed a Rust build, so writing a small one was easier.

**Status:** Decided

### D-185 — Videos can be picked from Files

Videos can be picked from Files as well as the photo library, and Convert to MP4 asks every time where to pick from. iPhone cannot open MKV, WEBM or AVI, so those report that the phone cannot open them and suggest converting on a computer first. Whether to add FFmpeg for iPhone, which would enlarge the app, is left for later.

**Why:** Videos downloaded to a computer are usually not in the photo library.

**Status:** Decided

### D-186 — Word / Excel / PPT to PDF

Word, Excel, PowerPoint and RTF files can be converted to PDF in the PDF tool. On iOS the system prints the document; on Android only .docx is converted, and other formats report that they are unsupported. Not done: PDF to Word that keeps the original layout.

**Why:** Converting Office files to PDF is a top-ranked need, while PDF to Word that keeps the layout cannot be done well on the device.

### D-187 — Quick actions can "log an entry"

A quick action can log an entry: for each file, or piece of text, a form built from the table opens with today's date; the user fills it in and taps Save, and with several files can skip one. The file is saved as a Morph file and put in the table's first attachment field, and text goes into its first long-text field. The AI only picks the table. The attachment part was changed by D-263.

**Why:** The founder chose this on 2026-10-24: photographing a receipt and filing it in bookkeeping is the most common need across files and data.

### D-188 — Formula field

A formula field computes a value live from number, amount, rating, date and time fields in the same table, using plus, minus, times, divide and parentheses. Nothing is stored, so values are recalculated when shown, sorted, filtered, summed or exported. An empty field or a zero divisor gives no value. A restricted if was added later by D-246. Formulas cannot be filled in by the user. (The founder, 2026-10-26.)

**Why:** Four operations cover the most common calculations, such as unit price times quantity, tax, discounts and differences.

**Status:** Decided

**Changed later by:** D-246, D-247, D-281.

### D-189 — Collecting needs

When the AI cannot do a request, a 'Tell us you need this' button appears under the answer. Tapping it sends only that sentence, the language, the refusal reason and app details to the server; nothing is sent otherwise, and no files, entries, settings or device ID. The button can be turned off in Settings under AI and is hidden when no server is set. The privacy policy must say so before launch.

**Why:** The founder chose this on 2026-10-24: only this loop shows which tool to add next, and sending only on tap keeps data to a minimum.

**Status:** Decided

### D-190 — AI changes go into draft mode first

(`draft*` in `workspace/store.ts`, `mobile/src/draft/`): once the AI has finished, the AI change page closes and the App shows the changed result directly, **view only, not usable** (running, entries, picking images, adding tools, settings subpages and restoring Change history only say "available after you apply"). Four buttons joined at the bottom: **Change** (the bottom chat box; every sentence changes the draft one more step), **Step back** (grayed out when only one step is left), **Apply** (all steps are merged into one AI version, which can be undone), **Leave** (the draft is kept). There is one draft at a time, stored in `app_meta.draft`, which survives restarts and is re-applied on top of the latest version when you come back; steps that cannot be re-applied are dropped with a notice; if displaying fails, the most recent step is removed. The AI change page becomes an input box with a send arrow, two examples and "Pick a style" (the style choice of D-095 moves into a popup, and a choice goes straight into the draft); when a draft exists it shows "Continue / Delete (asks first)", and a new sentence continues editing that draft. The old preview page is removed: a new quick action goes on the home page by default (the checkbox of D-109 is removed; it is not placed if the user said not to, or if it was made for a shared file); "Undo" in a draft is Step back, and with no draft it goes straight back to the previous version; "Restore this version" in Change history now asks first before taking effect. After Apply: a new quick action → "Your quick action is ready"; one started from the inbox returns to the inbox (the shared files stay); "Let AI change this" → its "ready" screen (the old result page of D-126 is closed). Direct editing was closed at first; D-235 reopens long-press single-component editing, while the whole-page edit button stays closed

**Why:** The founder decided on 2026-10-24: seeing the changed result in the real App hits harder than a preview image, and continuous chat edits fit "keep reshaping the same App" better than one sentence at a time; the features are locked inside a draft so it cannot be confused with the real one, which also removes the problem of data being produced inside a draft. The number avoids D-177 and D-178, which the tool download design uses

**Status:** Decided

**Changed later by:** D-235, D-526.

### D-191 — AI changes split into two paths, "feature" and "look"

(core `ai/kinds.ts`, `change` in `workspace/store.ts`): feature = adding, removing and changing quick actions (including steps, parameters, renaming), adding / removing / updating tools, and table structure (creating a table, fields, deleting a table); the home-page entry of a new quick action goes with it. Everything else (theme, navigation bar, pages and the components on pages, including a table's list, form and statistics) is look, and the App decides by operation. Features **do not go into a draft**: they are saved directly as one AI version (banner at the top "Changed · Undo") and open "Your quick action is ready" (D-125; a newly created table opens "Your data table is ready", with "Add an entry now"). **One sentence never changes both kinds**: if there is a feature, only the feature is done (several features in the same sentence are done together), and the remaining look changes become **one** "Keep going" (new Plan field `next`; if the model gives none, the descriptions of those look operations are used; stored in `app_meta.next`, replaced by the next feature change and cleared when used or undone), on the "ready" page and also as the first example on the AI change page; tapping it sends automatically and goes into a draft. When a feature cannot be applied alone and can only be applied together with the look (deleting a field needs it removed from the form), those look changes are done together. "Create a bookkeeping page" = first create the "Transactions" table, then "add a bookkeeping page". The draft chat box changes only the look: a feature request gets an explanation of why, and can be taken to "Change this app" (**changed by D-411**: it now takes effect directly); while a draft exists, a feature said on the AI change page is applied directly, and the draft is kept and re-applied. Onboarding guide step 2, the inbox and "Let AI change this" all take the feature path; the built-in rule "simplify steps" no longer hides the description on the tool page as a side effect

**Why:** The founder decided on 2026-10-24: putting features such as quick actions and tools into a "view only, not usable" draft helps little; the preview of a feature is just trying it, and the sense of safety comes from being able to undo; only the look needs to be seen first. After the split every step is clearly one kind or the other, and a draft never contains a feature that cannot be used

**Status:** Decided; applying a sample app is an exception (D-262); the draft chat box sentence is changed by D-411

**Changed later by:** D-262, D-411, D-419.

### D-192 — AI quota for free users

(decided by the founder on 2026-10-23): new users get **50** uses once, then **20** per month (reset per calendar month, not accumulated; the one-time quota is used first, then the monthly quota). A use is deducted only when the server returns an applicable change plan (`kind: plan`); an AI refusal (`kind: reject`) or a request error (4xx/5xx) is not deducted. Undo does not refund uses (otherwise it could be used over and over without limit). The free quota uses **Claude Haiku 5.5**; the model and quota of paid tiers are set with pricing (P-008, P-010). The App shows the remaining uses and suggests upgrading when they are nearly gone. When the quota runs out the server returns 429

**Why:** Each change costs very little (Haiku about $0.0002, so 50 uses about $0.01); the quota exists mainly for conversion rather than cost. The AI is used only to change the App, and usage is concentrated in the first few days: 50 uses are enough to build the first one or two tools, 20 a month is enough for everyday tweaks but not for frequent large changes, which leaves room for a paid tier of hosted AI. Giving it per day (for example 20 a day) would almost never run out, which equals free forever. The numbers are estimates; after launch they are adjusted according to the distribution of new users' first-7-day usage in `ai_usage`

**Status:** Decided

**Changed later by:** D-193.

### D-193 — The server only relays model calls and does not know the App's version

The founder decided on 2026-10-24 that the server only relays model calls: the prompt, validation and repair run in the app, and the server forwards requests with an output cap and thinking settings. It accepts only the shape of planning requests, enforces daily cost limits per device and in total, and blocks devices that repeatedly send off-plan replies. Device attestation is still needed before store release. Changes D-192.

**Why:** The server no longer has to match each app's schema version, and the prompt is already public, so moving it into the app leaks nothing.

**Status:** Decided

### D-194 — PDF password removal and encryption

PDF tools can remove a password (`pdf.unlock`, which also accepts images) and add one (`pdf.protect`). Passwords are asked at run time and never kept in the config, history or run records, nor sent to the AI. Only iPhone can unlock PDFs, and unlocking copies pages into a new document, so bookmarks and document info are lost. Changes P-025, P-026, P-027.

**Why:** Password-protected files could not go through any step, and competitor apps list password removal and encryption as selling points.

**Status:** Decided

### D-195 — Scans become PDFs with searchable, copyable text

Scans from the Scan document preset get an invisible text layer, so the text can be searched and copied. Recognition runs on the device, and the text is written only into that PDF. Without system recognition, or where recognition fails on a page, that PDF or page stays an image. Changes P-028.

**Why:** Competitor apps are praised for searchable PDFs, while Morph scans had no text layer.

**Status:** Decided

**Changed later by:** D-266.

### D-196 — Each quick action remembers its own folder

Each quick action now remembers its own save folder. The last folder chosen anywhere is used first, and the picker opens only if none was ever chosen. "Other folder" changes only that quick action, and folders of deleted quick actions are forgotten when the app opens. Changes D-123, P-029.

**Why:** A single remembered folder for the whole app meant receipts, contracts and voice memos could only go to one place.

**Status:** Decided

### D-197 — Append to an existing file

The new file action `file.addExisting` places files before or after an existing PDF or image. At run time the user picks the target: by default this quick action's last result, or another file, or none. The choice is used only for that run and is not written into the config. An expense-report preset uses it, and the old copy is kept. Changes P-030.

**Why:** Appending receipts to an existing report meant finding the old file by hand, and only a workflow's first step could pick input.

**Status:** Decided

### D-198 — App lock

The founder decided on 2026-10-24 not to build an app lock for now. The planned version would use Face ID, Touch ID or the phone passcode, be off by default, and be stored on the device, not in the config. Not done: a Morph-own password.
