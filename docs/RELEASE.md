# Releasing the app to the stores

This covers what a store release needs beyond the local build. The build and install command, with the four `EXPO_PUBLIC_*` variables, is in `AGENTS.md` under "Building a release build". The relay server's deploy and rollback are in `docs/DEPLOY.md`. Pushing, uploading and submitting happen only when the founder asks.

State on 2026-11-22: nothing has been published to either store.

## Before every upload

1. Run `npm run check` on the commit you will release.
2. Build the release with the command in `AGENTS.md`.
3. Run the smoke test on an emulator (`npm run smoke:android -- --apk <apk> --serial <emulator serial>`).
4. Go through `docs/RELEASE_CHECKLIST.md` on a device.
5. Raise the build number (see "Versions").
6. After uploading, tag the commit and keep the uploaded file (see "Keeping what was released").

## Versions

- `expo.version` in `apps/mobile/app.json` is the version users see (`1.0.0`).
- Every upload needs a higher build number:
  - iOS: `ios.buildNumber` (`"1"` on main).
  - Android: `android.versionCode`. It is not set on main. Branch `claude/google-play-closed-testing-eba026` (commit 912ec061, not merged) sets it to 1 for the first Play upload.
- `app.json` is the only place these numbers live. Change them in the same commit as the release.

## Android (Google Play)

- **Package**: `dev.stonetech.tinkrum` (D-553).
- **Two keys, two kinds of build**:
  - Builds installed on the founder's phone with `adb` are signed with the Expo template's debug key. That keeps his data across installs.
  - Store builds are signed with the upload key, `~/.android/tinkrum-play/tinkrum-upload.jks`. Its password is in a file beside it. Both stay outside the repository and are never printed or committed. The certificate is "CN=Tinkrum Upload, O=Stonetech", SHA-256 `B6:45:3F:BC:FC:B0:CF:4A:83:85:B9:83:A5:4D:B1:73:EF:B5:EF:1F:83:C7:42:95:EA:4B:65:EB:93:A1:4A:6C`.
  - Keep a backup of the key outside this Mac. Without it, an update can only be uploaded after Google resets the upload key.
- **The two kinds of build cannot replace each other.** A Play build cannot update an `adb`-installed debug-key build, or the other way round. Switching means uninstalling, and because `allowBackup` is false, uninstalling deletes every record and file. Say this to the founder before any switch.
- **Signing is not in the repository yet.** `apps/mobile/android/` is regenerated by prebuild, so a signing config written there disappears. Making it permanent needs a config plugin that reads the key's path and password from outside the repository. That is a code change that needs the founder's yes.
- **Already built**: on 2026-11-21 an app bundle (AAB) was built from 3a69d566, with versionCode 1, signed with the upload key. It is in `~/Library/Application Support/Claude/side-session-notes/android-release/20261121-play-aab-3a69d566/` with its R8 `mapping.txt`. Whether it was uploaded is not recorded here; check the Play Console.
- **Play Console, done by the founder**: the app record; Play App Signing; the data safety form; the store listing (texts in three languages, screenshots, icon, feature graphic); the privacy policy URL. A personal developer account also needs a closed test before production, with a minimum number of testers over a minimum number of days. Check Google's current rule in the console.

  - Ask the founder before changing signing.
- **Open, for the founder**:
  - Export compliance (`ITSAppUsesNonExemptEncryption`). It is not set on main; an uncommitted change in the TestFlight session's worktree sets it to `false`.

  - The App Store privacy labels.
- **App Review**: guidelines 2.5.2 and 4.7 (no downloaded code changes what the app does) and 3.1 if subscriptions are ever sold. Whitelisted components and quick actions that cannot loop are the main argument (see the product background in `AGENTS.md`, §8).

## What the store declarations must say

The facts, from the invariants and the code:

- Records, files, recognised text and recordings never leave the phone.
- When the user asks Tink for a change, the relay receives the sentence and the structure of the app, never the records (invariants 1 and 2).
- The relay keeps those requests only when `MORPH_REQUESTS_FILE` is set on the server (D-240). Production leaves it unset (D-new-trusting-franklin-1). The app's note, the website and the privacy policy must change before it is turned on.
- Downloads of extension packs and tools come from fixed addresses and carry no user data.
- No account, no ads, no analytics, no crash reporting. The rescue page shares an error only through the system share sheet when the user taps it.

## Licenses

`THIRD_PARTY_NOTICES.md` lists what the app includes or downloads; the licenses were checked against the publishers' pages on 2026-11-22. Store builds should also show these notices inside the app. That page does not exist yet, and building it is a code change that needs the founder's yes.

## Keeping what was released

- Tag the released commit `app-<version>-<platform>-<build>` (for example `app-1.0.0-android-1`). Pushing the tag happens only with the founder's yes.
- Keep the uploaded AAB or IPA, and Android's `mapping.txt`, in `~/Library/Application Support/Claude/side-session-notes/android-release/<date>-<what>-<commit>/` (or `ios-release/`). Not in git.
- Without `mapping.txt`, crash stacks from that build cannot be read.
